## 一、P0 致命（3 条，必须马上改）

### P0-1 · 每日任务必然崩溃，提醒推送 100% 不工作

**位置**：`backend/app/jobs/daily.py:24`

```python
async with SessionLocal() as session:      # ← 没有 session.info["rls_user_id"]
    updated = await profile.refresh_weights(session)
    result = await reminder.run_daily(session, reference)
```

**实测复现**（在真实库上跑的）：

```
[1] 无 rls_user_id 查 persons -> 异常:
    ProgrammingError (psycopg.errors.UndefinedObject)
    unrecognized configuration parameter "app.user_id"
[2] 有 rls_user_id 查 persons -> OK，行数 1
```

**为什么**：迁移 `0002` 的策略写的是
`USING (user_id = current_setting('app.user_id')::bigint)`——
`current_setting` 没传 `missing_ok=true`，变量缺失时**直接报错**（这是刻意设计，fail loud）。
项目里所有 session 入口都靠 `db.py` 的 `after_begin` 事件补这个变量，
**只有 `jobs/daily.py` 这一处没补**。

**后果**：
- `uv run python -m app.jobs.daily` 一跑就炸，权重刷新和提醒生成全都不发生
- 用户永远收不到提醒——这是整个 W9 的交付目标

**修法**（每日任务必须按用户逐个跑，不能一个 session 扫全表）：

```python
async def run_once(today: date | None = None) -> reminder.ScanResult:
    reference = today or datetime.now(UTC).date()
    result = reminder.ScanResult()

    # ① users 表没开 RLS，用无变量的系统 session 取活跃用户
    async with SessionLocal() as probe:
        user_ids = list(
            (await probe.execute(select(User.id).where(User.is_active.is_(True))))
            .scalars()
            .all()
        )

    # ② 每个用户单独一个 session，各自带自己的 RLS 变量
    for user_id in user_ids:
        async with SessionLocal() as session:
            session.info["rls_user_id"] = user_id
            updated = await profile.refresh_weights(session)
            partial = await reminder.run_daily(session, reference)
        result.created += partial.created
        result.sent += partial.sent
        result.failed += partial.failed
        logger.info("daily for user=%s weights=%s", user_id, updated)

    return result
```

> ⚠️ 顺带：`reminder.send()` 里调 `notify.push(session, reminder.user_id, ...)`，
> 通道查询也依赖 RLS。上面的改法同时修好了这一点。

### P0-2 · 节日提醒写入时被数据库直接拒绝

**位置**：`backend/app/services/reminder.py:44`

```python
LEVEL_NAMES = {7: "d7", 3: "d3", 0: "d0", 2: "d2"}   # ← d2 不在库里允许的范围内
LEVELS = {"birthday": (7, 3, 0), "payment_due": (3, 0), "festival": (2,), "custom": (3, 0)}
```

**实测复现**（直接问数据库）：

```
ck_reminder_level = CHECK (((level)::text = ANY
    ((ARRAY['d7','d3','d0'])::text[])))
```

**后果**：春节 / 端午 / 中秋 这类节日，T-2 那天生成提醒 → 写入 `d2` → 被 CHECK 拒绝 →
抛 `IntegrityError`。而 `run_daily` 的循环**没有 try/except**，
一条节日提醒失败会**连带把后面所有人的提醒全部打断**。

**修法**（二选一，推荐 A）：

- **A（改代码，不动库）**：节日档位改成 T-3

  ```python
  LEVELS = {..., "festival": (3,), ...}
  LEVEL_NAMES = {7: "d7", 3: "d3", 0: "d0"}     # 删掉 2
  ```
  同步改 `services/today.py:33` 的 `LEVEL_PRIORITY`（也列了 `"d2": 1`）。

- **B（改库，保留 T-2）**：新迁移 `0005`，把 CHECK 扩成 `('d7','d3','d2','d0')`。

> 顺带给 `run_daily` 的循环加一层保护，一条失败不要带崩全部：
> ```python
> for draft in await scan_due_events(session, reference):
>     try:
>         reminder, created = await upsert_reminder(session, draft)
>         ...
>     except Exception:                       # noqa: BLE001 — 单条失败不影响别人
>         logger.exception("reminder failed event_id=%s", draft.event_id)
>         result.failed += 1
> ```

### P0-3 · 生产环境 web 容器是个空壳，前端根本起不来

**位置**：`frontend/Dockerfile`

```dockerfile
FROM alpine:3.20          # ← 镜像里没有 caddy 二进制
WORKDIR /srv
COPY --from=build /app/dist /srv
CMD ["true"]              # ← 起来就退出
```

`docker-compose.yml` 把 `Caddyfile` 挂进了 `/etc/caddy/Caddyfile`，
但容器里**没有任何程序去读它**。`CMD ["true"]` 让容器立刻退出，
`restart: unless-stopped` 让它无限重启。

**后果**：`./deploy.sh` 会打印"部署完成，接口正常"（它只探了本机的 80 端口，
而 80 上其实没人监听——如果探到了说明 Caddy 没起但 nginx 之类占了，更隐蔽）。
**80/443 上没有任何服务，浏览器打不开，页面白屏。**

**修法**（把前端 Dockerfile 的最后阶段换成官方 Caddy 镜像）：

```dockerfile
# 前端镜像：构建静态文件 → 交给 Caddy 托管
FROM node:22-alpine AS build
WORKDIR /app
RUN corepack enable
COPY package.json pnpm-lock.yaml* ./
RUN pnpm install --no-frozen-lockfile
COPY . .
RUN pnpm build

FROM caddy:2-alpine                      # ← 换成这个
COPY --from=build /app/dist /srv
# Caddyfile 继续由 compose 挂进去，保持可改
```

同时 `docker-compose.yml` 的 web 服务加上：

```yaml
  web:
    build: ./frontend
    depends_on: [app]
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data
      - caddy_config:/config
    ports: ["80:80", "443:443"]
    restart: unless-stopped
```

> 顺带：Caddyfile 里补一个 HSTS 头会更稳：
> `header Strict-Transport-Security "max-age=31536000"`

### P1-1 · 管理接口没有 CSRF 防护

**位置**：`backend/app/api/admin.py:78`（`POST ""` 建号）、`:124`（`PATCH /{user_id}` 改密码/改角色/禁用）

这两个装饰器都没有 `dependencies=[Depends(require_csrf)]`——

**修法**：两个装饰器都加上 `dependencies=[Depends(require_csrf)]`。

### P1-2 · "归属待定"卡片点了没反应，W6 这条链路前端是断的

**位置**：
- 后端 `services/confirm.py:302` —— 归属待定组的 `ConfirmationItem.id` 装的是 **`raw_input.id`**，不是 `fact.id`
- 前端 `views/ConfirmView.vue:100 / :107 / :63` —— 一律拿 `item.id` 去调 `/confirmations/{id}/confirm`
- 前端 `ConfirmView.vue` **完全没有调用** 后端的 `PATCH /confirmations/{fact_id}`（reassign）

**后果**：
1. 在"归属待定"分组里点确认 → 后端拿 raw_input_id 去查 Fact → 404
2. 前端 `confirmOne` 只有 `finally` 没有 `catch` → Promise rejection 被吞 → **用户点了没反应，界面毫无提示**
3. "全部确认"会把 raw_input_id 混进 `fact_ids` 批量提交
4. **W6 的核心交互"AI 判不出是谁 → 用户指一个人"在 UI 上根本不存在**

**修法**（这条要动后端，不只是前端）：

1. 后端给 `ConfirmationItem` 加 `kind: Literal["fact", "unassigned"]`，让前端能分叉
2. 归属待定**目前没有 fact 记录**，只有 `raw_input` + `chat_segments`。
   现有的 `PATCH /confirmations/{fact_id}`（按 fact_id 改归属）**处理不了它**。
   → 需要**新增一个接口**：`POST /api/raw-inputs/{id}/assign`，入参 `person_id`，
   把 raw_input.person_id 设上 + 把它下面的 chat_segments 的 person_id 一起改掉，
   然后**直接触发一次该 raw_input 的重新抽取**（复用 `extract_from_raw_input`），
   这样事实才会真正落出来。
3. 前端归属待定卡片改成"选人 → 确认"，走上面这个接口
4. 前端所有请求包一层 catch，失败要给用户看到

### P1-4 · 农历生日在日历上显示两条

**位置**：`services/event.py:74` + `:92`

1. `create_event` 建农历生日时（`:210`）会把 `lunar` 回写进 `relationship.birthday_lunar`

**修法**：`_relationship_birthdays` 里排除"这个人已经有一条 lunar 生日事件"的情况：

async def _relationship_birthdays(session, start, end, covered: set[int]):

    for relationship, nickname in rows:

### P1-5 · 上传先把整个文件读进内存，再判大小

**位置**：`backend/app/api/ingest.py:98-105`

```python
content = await upload.read()                 # ← 先全读
if len(content) > limit:                      # ← 后判
    raise AppError(...)
```

**后果**：`MAX_UPLOAD_MB=8` 形同虚设。发一个 500MB 的请求体，进程就吃掉 500MB 内存；
10 张并发就是 5GB。**这是唯一一条能被外部直接打崩进程的路径。**

**修法**（读够就停）：

```python
chunk_limit = settings.max_upload_mb * 1024 * 1024
content = await upload.read(chunk_limit + 1)      # 多读 1 字节判断是否超限
if len(content) > chunk_limit:
    raise AppError(ErrorCode.FILE_TOO_LARGE, f"单张不能超过 {settings.max_upload_mb}MB",
                   status_code=413, detail={"max_mb": settings.max_upload_mb})
```

## 六、做得好的地方（这些别动）

评审不只是挑毛病，下面这些是真的做对了，改的时候别顺手改坏：

1. **六条铁律守得住** —— 55 个文件里，`services/` 没有一处 import fastapi，
   `api/` 的路由函数都短，`models/` 没有一句 `select()`，业务查询**没有一处写 `where user_id`**。
   这是这个项目最值钱的资产。
2. **RLS 设计是对的** —— `ENABLE + FORCE` 双开、`USING` 和 `WITH CHECK` 双写、
   `current_setting` 不传 `missing_ok`（fail loud 而非 fail silent）。
   **owner 角色也绕不过去**，这在国内项目里很少见。
3. **"抽错比不抽更糟"这条原则贯彻到了代码里** ——
   `no evidence → 丢弃`、`no reasons → 降级成只报日期`、`Key 没配 → 宁可标 failed 也不编内容`。
   这是整个产品的灵魂，别为了"看起来聪明"把它去掉。
4. **工程细节到位** —— 统一信封 + `response_model`、`X-Trace-Id` 头体一致、
   401 带 `WWW-Authenticate`、409 处理 `IntegrityError`、`_escape_like` 防通配符注入。
5. **提醒的幂等靠数据库唯一约束兜底**（不靠应用层判断），这个选择是对的。
