## 2. 核心改造：Person × Relationship 拆分

### 2.1 为什么必须拆

原方案里 `Person.type` 是枚举（哥姐/客户/其他），一个人只能属于一类。

但 L1 用户的真实情况是：**哥姐就是客户**。同一个人身上同时存在打赏关系和交易关系，且两种关系的时间线是交织的。

如果按 type 枚举设计，会有三个连锁问题：

1. 一个人只能记一套关系阶段、一套预算、一套话术
2. 打赏和订单要分开算价值（实际应该合并）
3. 一个人从"哥姐"转成"客户"时，历史数据要迁移

### 2.2 拆法

| 表 | 装什么 | 变更频率 |
|---|---|---|
| **persons** | 这个人的**客观身份**：昵称、平台 ID、手机号、头像、备注 | 极低 |
| **relationships** | 这个人跟**我的关系**：角色、阶段、价值、预算、禁忌、温度 | 高 |

```
persons  1 ──── 1  relationships（单用户场景）
persons  1 ──── N  relationships（多用户场景，user_id 区分）
```

**Relationship 的 `roles` 是数组，不是枚举。** 一个人可以同时是 `["ge_jie", "customer"]`，且每个角色可以有各自的阶段：

```json
{
  "roles": ["ge_jie", "customer"],
  "role_stages": {
    "ge_jie": {"stage": "core", "since": "2024-03"},
    "customer": {"stage": "familiar", "since": "2025-11"}
  }
}
```

**价值合并计算**：`relationships.total_value = 打赏 + 订单 + 转介绍估值`，不分角色。

### 2.3 附带好处

这个拆分让 V3 的泛化变简单了：换行业只需要换 `roles` 的取值和对应的字段模板，`persons` 完全不用动。

## 3. 记忆半衰期

### 3.1 问题

AI 抽取的事实不是永久的。"她孩子在高考"一年后就是错的；"她最近在装修"三个月后就失效。如果不处理，档案会越用越脏，最后用户不敢信。

### 3.2 设计

`facts` 表增加三个字段：

| 字段 | 作用 |
|---|---|
| `half_life_days` | 这条事实的半衰期（由抽取时按类别赋值） |
| `last_confirmed_at` | 最后一次被确认/更新/重新提到的时间 |
| `weight` | 当前权重 = `0.5 ^ (天数差 / half_life_days)` |

### 3.3 半衰期赋值表

| 类别 | half_life_days | 例子 |
|---|---|---|
| `permanent` 永久 | null | 生日、籍贯、血型 |
| `taboo` 禁忌 | 540 | 忌聊年龄、别提他儿子 |
| `structure` 结构 | 365 | 行业、家庭结构、职位 |
| `preference` 偏好 | 180 | 喜欢白茶、讨厌甜食 |
| `situation` 场景 | 60 | 装修中、孩子高考、最近生病 |
| `mood` 情绪 | 14 | 最近心情不好、刚升职很兴奋 |

### 3.4 使用规则

```
weight > 0.6   → 正常显示，可作为建议依据
0.3 < weight ≤ 0.6 → 显示为"可能已过期"，不作为强依据
weight ≤ 0.3   → 默认折叠，提示"这条还准吗？"
```

**关键**：`situation` 类过期后不是删除，是**降权 + 折叠**。因为"她去年在装修"仍是历史事实，只是不能当作现在的状态。

### 3.5 论文价值

这一节可以直接支撑"动态画像 vs 静态标签"的论点，并且可以做实验：**同一个档案库，带半衰期 vs 不带半衰期，在"建议准确率"上差多少。**

### 4.3 为什么这些表必须存在（答辩用）

| 表 | 评审会问什么 | 这张表怎么答 |
|---|---|---|
| `extraction_logs` | "AI 到底做了什么？" | 现场调一条：模型、prompt 版本、原始输出、用户处置，逐字段讲 |
| `agent_runs` | "它怎么知道该走 SQL 还是 RAG？" | 看路由决策和理由 |
| `temperature_snapshots` | "温度是怎么算的？" | 看历史值和五维因子分解 |

**这三张表不是工程需要，是可解释性的物证。** 没有它们，"AI 在干活"这句话在答辩现场是无法证明的。

### 4.4 多用户隔离（从第一天就要做）

数据库选 PostgreSQL 的直接原因是多用户，而多用户的正确做法**不是"应用层记得加 where user_id"**——人总会写漏，写漏就是数据泄漏。

Postgres 提供了数据库层的强制手段：**Row Level Security（RLS）**。

```sql
-- 一次配置，永久生效
ALTER TABLE persons        ENABLE ROW LEVEL SECURITY;
ALTER TABLE relationships  ENABLE ROW LEVEL SECURITY;
ALTER TABLE facts          ENABLE ROW LEVEL SECURITY;
ALTER TABLE ledger         ENABLE ROW LEVEL SECURITY;
ALTER TABLE events         ENABLE ROW LEVEL SECURITY;
ALTER TABLE todos          ENABLE ROW LEVEL SECURITY;
ALTER TABLE raw_inputs     ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON persons
  USING (user_id = current_setting('app.user_id')::int);
```

应用层每个请求开头设一次：

```python
session.execute(text("SET LOCAL app.user_id = :uid"), {"uid": current_user.id})
```

**四层防护，缺一不可**：

| 层 | 做法 | 如果漏了会怎样 |
|---|---|---|
| 表结构 | 每张业务表 `user_id NOT NULL` + 外键 | 数据无归属，后面无法补 |
| 数据库 RLS | 策略强制 `user_id = 当前用户` | 应用层写漏一个 where 就串数据 |
| 应用层 | 请求开始时 `SET LOCAL app.user_id` | RLS 拿不到变量，直接查不出东西（**会报错而不是静默泄漏，这是好事**） |
| 文件层 | `data/uploads/{user_id}/...` | 越权拿到别人的聊天截图 |

**两个必须现在就做的决定**：

1. **登录形态**：邀请制 + 邮箱密码，**不做开放注册**。种子用户是你自己和几个熟人，开放注册只会带来垃圾账号和隐私风险（这套系统存的是别人的私事）。
2. **删除权**：每个用户能一键导出、一键删除自己的全部数据。这既是合规底线，也是产品卖点。

> ⚠️ RLS 有一个坑：**超级用户和表所有者默认绕过 RLS**。所以应用连接要用一个**普通角色**（`keeper_app`），不要用 `postgres` 超级用户连。这一条写错，RLS 等于没开。

## 5. AI 链路设计

### 5.1 摄入链路（L1）：为什么分三步而不是一步

```
截图 → [① 识别] → [② 归属] → [③ 抽取] → 确认队列
```

| 步骤 | 问题 | 失败后果 | 重试成本 |
|---|---|---|---|
| ① 识别 | 是不是聊天记录？谁是谁？ | 整条链路白跑 | 低 |
| ② 归属 | 这是和谁的？ | 记到错的人身上 | 低 |
| ③ 抽取 | 有什么事实/事件/往来？ | 档案被污染 | 高 |

**分三步的原因**：

1. **失败可定位**：一步做完，抽错了不知道是看错图还是理解错
2. **可分别重试**：归属错了只重跑②，不用重新读图
3. **中间产物可展示**：每一步的输出都能给用户看，这是"可解释"的具体形态
4. **可分别评估**：论文里能按步骤报准确率，而不是一个笼统的数字

### 5.2 抽取 Prompt 骨架

```
角色：你是关系维护助手的信息抽取器。

输入：
- 一段聊天记录截图（或文字）
- 候选人物列表：[{id, nickname, aliases}]（最近 20 人）

任务分三步，逐步输出：

【第一步 · 识别】
1. 这是不是聊天记录？（是/否）
2. 如果是，提取每一句：说话人（me/other）、内容、时间（若截图中有）
3. 提取聊天对象的显示名（微信昵称/备注名）

【第二步 · 归属】
从候选列表中选择最可能的人，或返回 unknown。
必须给出理由：依据哪个昵称/称呼/上下文。

【第三步 · 抽取】
三类，每类可为空：
- facts：{content, category, confidence, evidence}
  category ∈ permanent|taboo|structure|preference|situation|mood
- events：{title, date, type, confidence, evidence}
- ledger：{direction, kind, amount, occurred_at, due_date, confidence, evidence}

硬约束：
1. 每条必须给 confidence（0-1）和 evidence（原文片段）
2. confidence < 0.7 的单独标记
3. 金额、生日、禁忌三类，confidence 阈值提高到 0.85
4. 不要编造。原文没有的信息一律不输出
5. 区分"事实"与"玩笑"：带有明显调侃语气的陈述，confidence 上限 0.6

输出：严格 JSON
```

**关于第 5 条**：这是实战中最容易翻车的地方——聊天里大量是玩笑和反话。把"我最近穷死了"抽成"经济困难"，会直接毁掉档案。

### 5.3 提醒生成链路（L2）

```
事件命中 → 四路取数 → 生成 → 推送
```

四路取数缺一不可：

| 来源 | 取什么 | 缺了会怎样 |
|---|---|---|
| 档案 | 硬字段 + 标签 + 综述 | 建议是通用的，不针对这个人 |
| 记忆层 | 关于这件事他说过的原话 | 建议没有依据 |
| 知识层 | 这类人/这个预算送什么 | 建议没有专业度 |
| 历史往来 | 往年送过什么 | 会重复送礼（用户最痛的点） |

Prompt 的硬要求（对应原则二、三）：

```
1. 每条建议必须写成"因为 [来源]，所以建议 [结论]"
2. 若档案有禁忌，必须在建议中显式规避
3. 若往年送过同类，必须提示并给替代方案
4. 不输出精确金额对比（禁止："他刷了 8000，你回 800"）
5. 给 2-3 个选项，不要只给一个（控制权在人手里）
6. 话术要口语化，像人说的话，不要像客服
```

### 5.4 关系温度模型（V2）

温度不是 AI 判断，是**可解释的加权计算**。这一点很重要——它意味着温度是稳定、可复现、可答辩的。

**五维因子**：

| 因子 | 计算 | 权重 | 为什么 |
|---|---|---|---|
| `recency` 新近度 | `exp(-天数/30)` | 30% | 越久没联系越冷，指数衰减 |
| `frequency` 频率 | 近 30 天互动次数 ÷ 历史月均 | 25% | 相对自己的基线，不是绝对值 |
| `quality` 质量 | 平均对话轮次 + 主动发起比例 | 20% | 长对话 > 短问答 |
| `value` 价值 | 近 90 天金额趋势 vs 历史 | 15% | 打赏/订单在降是强信号 |
| `initiative` 主动性 | 他主动 ÷ 总互动 | 10% | 他主动找你说明关系好 |

```
temp_score = 100 × (0.30·recency + 0.25·frequency + 0.20·quality + 0.15·value + 0.10·initiative)
```

**关键设计：频率必须相对自己的基线算，不能算绝对值。** 一个本来一周聊一次的人，变成两周聊一次是信号；一个本来就一月聊一次的人，两周聊一次反而是升温。用绝对值会把所有人都判成冷的。

**误报控制（必须做）**：

1. **多因子同降才报警**：单个因子下降不足以判定，至少三个因子同时下降
2. **措辞留余地**：说"可能"，说"也许只是忙"，不说"他疏远了"
3. **温度只用于排序和提示，不用于自动发消息**
4. **下降超过 20 分才推送**，小幅波动不打扰

### 5.5 问答路由（V2）

```
用户提问 → 意图分类（LLM）→ 四类之一
    ├─ exact_fact    → SQL，直接查字段
    ├─ cross_person  → SQL + tags 表筛选
    ├─ fuzzy_recall  → 向量检索（按 person 分区）
    └─ knowledge     → 知识库 + 该人档案
```

**为什么必须路由而不能全用 RAG**：见 `01` 第 6.4 节。这一章是要做对比实验的——同一批问题，纯 RAG vs 混合路由，准确率差多少。这是论文里最扎实的一节数据。

### 5.6 向量检索的"按人分区"

检索前先锁定 `person_id`，再在该人的切片里做语义检索。原因：

- 用户的问题几乎总是关于某个具体的人
- 全库检索会把别人的私事混进来，这是**灾难性错误**
- 分区后召回率高、延迟低

代价：跨人检索（"谁提过想买茶"）不能用向量，必须走 SQL + 标签。这正好是路由存在的理由。

```

│  浏览器：Vue 3 SPA + Tailwind                  │
│  （响应式，手机优先，PWA）                        │
```

## 7. 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 后端 | **Python + FastAPI** | AI 生态成熟，异步支持好，省一半工期 |
| 前端 | **Vue 3 + TypeScript + Vite + Tailwind** | 模板语法接近 HTML，响应式自动追踪，对前端一般的人心智负担最低（详见 `05`） |
| 日历 | **FullCalendar 6.x（MIT 核心版）** | rrule 插件免费、`eventContent` 可渲染 HTML |
| 数据库 | **PostgreSQL 17** | 多用户、RLS 行级隔离、JSONB、并发写；从第一天就按多用户设计 |
| 向量 | **pgvector** | 与主库同实例，RAG 记忆层不用另起向量服务 |
| 模型 | **DeepSeek `deepseek-flash`（主）→ `qwen-vl-max`（备）** | 国内直连、OpenAI 兼容、一张图 ≤384 tokens；`VisionClient` 抽象可切 |
| 农历 | **lunar-python + chinese-calendar** | 均 MIT；一个管换算，一个管法定节假日 |
| 推送 | **企业微信 webhook → PushPlus** | 免费、无需营业执照、服务端一个 POST |
| 定时 | **APScheduler** | 单机够用，不用上 Celery |
| 部署 | **Docker + Caddy** | 自动 HTTPS，一条命令起 |

### 7.1 已排除方案（写进论文"选型对比"）

| 方案 | 排除理由 |
|---|---|
| 微信 ClawBot / iLink | 官方通道，但**不支持主动推送**，只能被动回复 24h 内发过消息的用户 |
| 个人号 hook / wechaty | 违反微信许可协议，可封号 |
| 微信小程序 | 订阅消息为一次性授权，长期提醒受限；需备案域名 + 另写一套 |
| PWA Web Push | 国内 Android 走 FCM 不通，iOS 需先添加到主屏 |
| CalDAV 服务器 | GPL 传染、事件存 .ics、自家对象塞不进 VEVENT |
| 纯 RAG | 精确事实和跨人筛选上准确率显著低于 SQL |

## 8. 成本估算

### 8.1 模型调用

假设每天投喂 8 张截图 + 20 条文字：

| 项 | 次数/月 | 单价（便宜 VLM） | 月成本 |
|---|---|---|---|
| 截图抽取（VLM） | 240 | $0.003 | **$0.7** |
| 文字抽取（LLM） | 600 | $0.0003 | **$0.2** |
| 建议生成 | 30 | $0.01 | **$0.3** |
| 综述重写 | 200 | $0.001 | **$0.2** |
| 合计 | | | **约 $1.5 / 月** |

用中高端模型（Claude/GPT-4o 级别）大约是 **$10-15 / 月**。

**结论：模型成本可以忽略，瓶颈不在这里。** 真正的成本是服务器（约 100-300 元/月）和你的时间。

### 8.2 服务器

| 项 | 规格 | 成本 |
|---|---|---|
| 云服务器 | 1 核 2G | 100-300 元/月（国内）/ $5-6（海外） |
| 域名 + HTTPS | Caddy 自动证书 | 域名 ~50 元/年 |
| 存储 | 截图（每月约 300 张 × 500KB） | 可忽略 |

### 8.3 省钱设计

- 截图先本地预处理（压缩、裁边），再上传
- 抽取用便宜模型，建议生成用强模型（分级调用）
- 同一张图（hash 相同）不重复调用
- 离线回放模式：演示用 fixture，不调模型

## 9. 可解释性的具体形态

论文里"可解释性"最容易被写成空话。这里给出可落地的四条：

| 层面 | 具体做法 | 用户/评审能看到什么 |
|---|---|---|
| **数据级** | 每条事实带 `evidence` + `source_id` | 点一下看到原图，知道这句话从哪来 |
| **决策级** | 路由决策 + 理由写入 `agent_runs` | "为什么这个问题走了 SQL 而不是 RAG" |
| **算法级** | 温度五因子分解存 `factors` JSON | "78 分是怎么来的"——每个因子多少分 |
| **行为级** | 建议必带依据链 | "因为 A，所以建议 B" |

**四条缺一条，"AI 在干活"这句话就有一块说不清。**
