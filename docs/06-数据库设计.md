## 0. 这份文档怎么用

| 角色 | 怎么用 |
|---|---|
| 开发时 | 建表、改字段、写查询，全部以本文为准 |
| 写 Migration 时 | 先对照本文，改完再对照回来确认一致 |
| 答辩时 | 评审问"字段为什么这么设计"，直接翻第 7 节范式校验 |
| 改需求时 | 先看第 2 节业务对象有没有变，再动表 |

**铁律：数据库结构变更 = 先改本文 → 再改 Migration → 最后执行。**
不允许直接在数据库里 `ALTER TABLE`，那样第二天就没人知道线上是什么结构了。

## 1. 设计原则

这份设计是按"从业务长出来"的顺序做的，不是从功能模块推的。

```
业务流程 → 找业务对象 → 确认对象关系 → 选数据库
→ 设计字段 → 范式校验 → 生成 Migration → 跑通 → 提交 Git
```

四条自我约束：

1. **业务对象优先于表**：先想清楚"有哪些东西"，再想"用几张表装"
2. **能解释每个字段为什么存在**：解释不了的字段，删掉
3. **反范式必须给理由**：本文第 7 节每一条都标了原因
4. **先跑通再扩展**：V1 只保证"能连、能建、能增删查"，不做性能优化

## 3. 对象关系

### 3.1 关系图

```
用户 1 ──< N  人
         1 ──< N  原始材料
         1 ──< N  事件
         1 ──< N  待办

人   1 ── 1  关系              ← 一段关系，多个角色
     1 ──< N  事实
     1 ──< N  往来
     1 ──< N  对话片段
     1 ──< N  原始材料
     1 ──< N  事件（可空）
     1 ──< N  待办（可空）

原始材料 1 ──< N  对话片段
         1 ──< N  事实（多态，无外键）

事实   1 ──< N  标签

事件   1 ──< N  提醒

往来   1 ── 0..1  事件（有 due_date 才生成）
```

### 3.2 关系判定说明

| 关系 | 类型 | 关联字段放哪 | 为什么 |
|---|---|---|---|
| 用户 ↔ 人 | 1:N | `persons.user_id` | 一个人只属于一个用户（不做团队共享） |
| 人 ↔ 关系 | **1:1** | `relationships.person_id` **唯一** | 你和一个联系人只有一段关系；多角色用数组表达，不拆多行 |
| 人 ↔ 往来 | 1:N | `ledger.person_id` | 一个人多笔钱 |
| 人 ↔ 事实 | 1:N | `facts.person_id` | 一个人多条记忆 |
| 事件 ↔ 提醒 | 1:N | `reminders.event_id` | 一个生日三个档（7/3/当天） |
| 往来 ↔ 事件 | 1:0..1 | `events.source_type/source_id` | 只有带 `due_date` 的往来才生成结款事件 |

### 3.3 三处有意的"不做外键"

按方法论，该给理由：

**① `facts.source` 用 `source_type` + `source_id` 多态**
事实可能来自截图（`raw_inputs`），也可能来自一句话（也是 `raw_inputs`，但 `kind=text`）。理论上可以合并成一个外键，但**保留多态是为了以后能挂到别的地方**（比如从问答里确认的事实）。代价是没有数据库级引用完整性，靠应用层保证。

**② `relationships.roles` 用 JSON 数组**
一个人同时是哥姐和客户，用关联表需要 `persons_roles(person_id, role)` 三张表，但角色只有 3-4 个值且几乎不查"哪些人是哥姐"。**用数组够用，拆表是过度设计。**

**③ `persons.platform_ids` / `contact` 用 JSON**
微信/抖音/快手 ID、手机/地址。典型的多值属性，按 1NF 该拆表。但它们**几乎不参与查询**——你不会按"抖音号 138xxx"搜人，只会按昵称搜。低频字段拆表只会让每次读档案多两次 join。
**代价**：JSON 里的字段没法加唯一约束，需要应用层去重。

### 3.4 一处会让人犹豫的：`persons` 与 `relationships` 为什么不合并

1:1 关系按方法论可以合并（把字段塞进同一张表）。这里拆开的三个理由：

1. **更新频率差一个数量级**：身份（昵称、平台号）几乎不变；关系（温度、总金额、最后互动时间）天天变。分开后，高频更新不影响身份表的索引
2. **语义不同**：`persons` 的主对象是"这个人"，`relationships` 的主对象是"我跟这个人的一段关系"——符合第二范式"字段围绕当前表的主对象"
3. **扩展不返工**：将来要加"关系历史"或"一个人在多场景下不同的关系"，`relationships` 表能直接一对多，不用拆表迁移数据

**代价**：读档案要 join 两张表，但这个查询一天不到几百次，完全不是瓶颈。

## 4. 数据库选型

| 项 | 选择 | 理由 |
|---|---|---|
| **主库** | **PostgreSQL 17** | 多用户隔离靠 RLS（数据库层强制）；JSONB 可索引；pgvector 同实例；并发写强 |
| **向量** | **pgvector** | 不用另起向量数据库，少一套运维 |
| **缓存** | **不用 Redis** | 20 人规模没有缓存需求，会话用签名 cookie，不需要共享存储 |
| **队列** | **不用** | 定时任务用 APScheduler 跑在进程内；上传处理用 FastAPI BackgroundTasks |

**为什么不是 MySQL**：MySQL 没有 RLS，多用户隔离只能靠应用层写 `where user_id`，总会漏。
**为什么不是 SQLite**：SQLite 没有行级安全（[详见 `05` 4.3]）。

> ⚠️ 不使用 Redis 是一条明确决定，不是"以后再加"。理由：一旦引入 Redis，部署多一个容器、备份多一套、故障多一种可能，而 20 人规模它一个收益都带不来。

## 5. 表结构

### 5.1 通用约定（先看这个，后面不再重复）

| 约定 | 规则 |
|---|---|
| **命名** | 全小写英文 + 下划线，表名复数（`persons`），字段名单数（`nickname`） |
| **主键** | `id bigserial`，自增。不用 UUID（个人项目不暴露用户数，且自增索引更小） |
| **时间** | 全部 `timestamptz`，**存 UTC**，显示时转 `Asia/Shanghai` |
| **时间自动维护** | `created_at DEFAULT now()`，`updated_at` 由触发器维护 |
| **软删除** | **V1 不用软删除**。删除即真删（用户明确要求"全删不留痕"） |
| **金额** | `numeric(12,2)`，**永远存正数**，方向由 `direction` 字段表达 |
| **状态** | `text` + `CHECK` 约束，**不用数据库 ENUM 类型**（ENUM 加值要改类型，麻烦） |
| **布尔** | `boolean`，字段名带 `is_` 前缀 |
| **外键** | 显式写 `ON DELETE` 行为，不允许默认（默认是 NO ACTION，会报错） |
| **索引** | 每个外键都建索引；查询条件里的字段建索引 |

### 5.2 `users` — 用户

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigserial | PK | |
| `username` | text | UNIQUE NOT NULL | **统一登录名**：用户名/手机号/邮箱都填这里，不校验格式 |
| `display_name` | text | | 界面上显示的名字 |
| `password_hash` | text | NOT NULL | argon2id，**绝不存明文** |
| `role` | text | NOT NULL DEFAULT 'member' | `owner` \| `member` |
| `is_active` | boolean | NOT NULL DEFAULT true | 禁用账号用这个，不删用户 |
| `failed_attempts` | int | NOT NULL DEFAULT 0 | 连续登录失败次数 |
| `locked_until` | timestamptz | | 锁定到期时间 |
| `last_login_at` | timestamptz | | |
| `keep_original_images` | boolean | NOT NULL DEFAULT true | **原图留存开关**：关掉后新上传的图处理完即删，只留文字 |
| `created_at` | timestamptz | NOT NULL DEFAULT now() | |
| `updated_at` | timestamptz | NOT NULL DEFAULT now() | |

**索引**：`username` 唯一索引；`is_active` 部分索引（查有效用户）。

**为什么没有 email / phone 字段**：按 `05` 4.2.1 的决定，V1 不做真实性验证。将来要上短信，加 `phone` + `phone_verified_at` 两列即可。

### 5.3 `persons` — 人（客观身份）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigserial | PK | |
| `user_id` | bigint | NOT NULL FK `users` ON DELETE CASCADE | 数据归属 |
| `nickname` | text | NOT NULL | 主称呼（"王姐"） |
| `aliases` | jsonb | NOT NULL DEFAULT '[]' | 其他称呼：微信名、抖音昵称、你起的绰号 |
| `platform_ids` | jsonb | NOT NULL DEFAULT '{}' | `{wechat: "...", douyin: "..."}` |
| `avatar_path` | text | | 头像文件路径 |
| `contact` | jsonb | NOT NULL DEFAULT '{}' | 手机/地址/其他 |
| `note` | text | | 自由备注 |
| `created_at` | timestamptz | NOT NULL DEFAULT now() | |
| `updated_at` | timestamptz | NOT NULL DEFAULT now() | |

**索引**：
- `(user_id)` — 列表查询
- `(user_id, nickname)` — 搜索
- `GIN (aliases jsonb_path_ops)` — 按别名搜人（归属判定时用）

**约束**：`UNIQUE(user_id, nickname)` **不加**。可能有两个"王姐"，强制唯一会挡路。重名靠头像和标签区分。

### 5.4 `relationships` — 关系（主观状态）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigserial | PK | |
| `user_id` | bigint | NOT NULL FK ON DELETE CASCADE | |
| `person_id` | bigint | **NOT NULL UNIQUE** FK `persons` ON DELETE CASCADE | 一个人一段关系 |
| `roles` | jsonb | NOT NULL DEFAULT '["ge_jie"]' | `["ge_jie","customer"]` |
| `stage` | text | NOT NULL DEFAULT 'new' | `new`\|`familiar`\|`core`\|`cold` |
| `stage_source` | text | NOT NULL DEFAULT 'auto' | `auto`\|`manual` — 系统算的还是人改的 |
| `stage_updated_at` | timestamptz | | 手动修改的时间，自动算法不覆盖 manual |
| `value_tier` | text | NOT NULL DEFAULT 'unknown' | `high`\|`mid`\|`low`\|`unknown` |
| `value_tier_source` | text | NOT NULL DEFAULT 'auto' | 同上 |
| `birthday_solar` | date | | 公历生日 |
| `birthday_lunar` | jsonb | | `{month, day, is_leap}` |
| `birthday_type` | text | | `solar`\|`lunar`（二选一） |
| `gift_budget_min` | numeric(12,2) | | 送礼预算下限 |
| `gift_budget_max` | numeric(12,2) | | 上限 |
| `taboo` | jsonb | NOT NULL DEFAULT '[]' | 禁忌话题列表 |
| `total_in` | numeric(12,2) | NOT NULL DEFAULT 0 | 他给我，累计 |
| `total_out` | numeric(12,2) | NOT NULL DEFAULT 0 | 我给他，累计 |
| `temp_score` | smallint | | 温度 0-100（V2） |
| `temp_trend` | smallint | | 近 30 天变化（V2） |
| `temp_updated_at` | timestamptz | | |
| `last_interaction_at` | timestamptz | | 最后互动时间 |
| `is_active` | boolean | NOT NULL DEFAULT true | 是否在活跃窗口（20 人） |
| `created_at` | timestamptz | NOT NULL DEFAULT now() | |
| `updated_at` | timestamptz | NOT NULL DEFAULT now() | |

**约束**：
- `UNIQUE(person_id)` — 强制 1:1
- `CHECK (birthday_type IN ('solar','lunar') OR birthday_type IS NULL)`
- `CHECK (gift_budget_min IS NULL OR gift_budget_max IS NULL OR gift_budget_min <= gift_budget_max)`
- `CHECK (temp_score BETWEEN 0 AND 100 OR temp_score IS NULL)`

**索引**：
- `(user_id, is_active)` — 活跃窗口查询
- `(user_id, stage)` — 阶段筛选
- `(birthday_solar)` 部分索引 `WHERE birthday_solar IS NOT NULL` — 生日扫描
- `(last_interaction_at DESC)` — 列表排序

**`total_in` / `total_out` 是冗余字段**，可以从 `ledger` 求和。理由见第 7 节。

### 5.5 `raw_inputs` — 原始材料

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigserial | PK | |
| `user_id` | bigint | NOT NULL FK ON DELETE CASCADE | |
| `person_id` | bigint | FK `persons` ON DELETE CASCADE | **可空**：归属判定前为空 |
| `kind` | text | NOT NULL | `screenshot`\|`text` |
| `file_path` | text | | 截图路径（`data/uploads/{user_id}/...`） |
| `file_hash` | text | | sha256，用于去重 |
| `ocr_text` | text | | OCR 出的纯文本 |
| `raw_text` | text | | 用户直接输入的一句话 |
| `status` | text | NOT NULL DEFAULT 'pending' | `pending`\|`processing`\|`done`\|`failed` |
| `error_msg` | text | | 失败原因 |
| `created_at` | timestamptz | NOT NULL DEFAULT now() | |
| `processed_at` | timestamptz | | 处理完成时间 |
| `file_deleted_at` | timestamptz | | **原图已清理**的时间。非空 = 只剩文字，界面上"查看原图"置灰 |

**约束**：`CHECK (kind IN ('screenshot','text'))`

**索引**：
- `(user_id, status)` — 待处理队列
- `(user_id, person_id)` — 按人查原始材料

**为什么 `person_id` 可空**：上传时还不知道是谁。AI 判定后再回填。**删除人时级联删除**（对应"全删不留痕"）。

### 5.6 `chat_segments` — 对话片段

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigserial | PK | |
| `raw_input_id` | bigint | NOT NULL FK `raw_inputs` ON DELETE CASCADE | |
| `person_id` | bigint | FK `persons` ON DELETE CASCADE | 冗余，方便按人检索 |
| `speaker` | text | NOT NULL | `me`\|`other` |
| `content` | text | NOT NULL | 这一句的内容 |
| `said_at` | timestamptz | | 截图里读到的时间，可能为空 |
| `said_at_inferred` | boolean | NOT NULL DEFAULT false | 时间是从上传时间推的，不是读出来的 |
| `seq` | int | NOT NULL | 在截图中的顺序，从 1 开始 |

**索引**：`(raw_input_id, seq)`、`(person_id, said_at DESC)`

**为什么 time 可能为空**：微信截图不一定每一屏都有时间戳。读不到就用上传时间兜底，但标记 `inferred=true`，避免误导。

### 5.7 `facts` — 事实（软记忆）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigserial | PK | |
| `user_id` | bigint | NOT NULL FK ON DELETE CASCADE | |
| `person_id` | bigint | NOT NULL FK `persons` ON DELETE CASCADE | |
| `content` | text | NOT NULL | "最近在喝白茶" |
| `category` | text | NOT NULL | `permanent`\|`taboo`\|`structure`\|`preference`\|`situation`\|`mood` |
| `half_life_days` | int | | 半衰期天数，`null` = 永久 |
| `weight` | real | NOT NULL DEFAULT 1.0 | 当前权重 0-1，随时间衰减 |
| `confidence` | real | NOT NULL | 抽取置信度 0-1 |
| `source_type` | text | NOT NULL | `screenshot`\|`text`\|`manual` |
| `source_id` | bigint | | 多态引用，指向 `raw_inputs.id` |
| `evidence` | text | | 原文片段，用于"查看出处" |
| `status` | text | NOT NULL DEFAULT 'pending' | `pending`\|`confirmed`\|`rejected` |
| `last_confirmed_at` | timestamptz | | 最后确认时间，衰减从这里算 |
| `created_at` | timestamptz | NOT NULL DEFAULT now() | |

**约束**：
- `CHECK (category IN (...))`
- `CHECK (confidence BETWEEN 0 AND 1)`
- `CHECK (weight BETWEEN 0 AND 1)`
- `CHECK (status IN ('pending','confirmed','rejected'))`

**索引**：
- `(person_id, status)` — 查某人的事实
- `(person_id, category)` — 按类别筛
- `(user_id, status)` — 待确认队列
- `(person_id, weight DESC)` — 按重要性排

**半衰期映射**（由 `category` 决定，应用层赋值）：

| category | half_life_days | 例子 |
|---|---|---|
| `permanent` | null | 生日、籍贯 |
| `taboo` | 540 | 忌聊年龄 |
| `structure` | 365 | 行业、家庭结构 |
| `preference` | 180 | 喜欢白茶 |
| `situation` | 60 | 装修中、孩子高考 |
| `mood` | 14 | 最近心情不好 |

### 5.8 `tags` — 标签（派生表）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | bigserial | PK | |
| `user_id` | bigint | NOT NULL FK ON DELETE CASCADE | |
| `person_id` | bigint | NOT NULL FK `persons` ON DELETE CASCADE | |
| `key` | text | NOT NULL | 维度：`industry`\|`family`\|`preference`\|`situation`\|`value`\|`stage` |
| `value` | text | NOT NULL | 值：`建材`\|`白茶`\|`装修中` |
| `source_fact_id` | bigint | FK `facts` ON DELETE SET NULL | 从哪条事实来的 |
| `expires_at` | timestamptz | | 过期时间（场景类标签才有） |
| `confidence` | real | | |
| `created_at` | timestamptz | NOT NULL DEFAULT now() | |

**约束**：`UNIQUE (person_id, key, value)` — 同一人的同一个标签只存一条

**索引**：
- `(user_id, key, value)` — **核心索引**：筛选"谁喜欢茶"
- `(person_id)` — 档案页读标签
- `(expires_at)` 部分索引 `WHERE expires_at IS NOT NULL` — 清理过期标签

**这是纯冗余表**，所有数据都能从 `facts` 算出来。理由见第 7 节。

### 5.9 `ledger` — 往来

| `direction` | text | NOT NULL | `in`（他给我）\|`out`（我给他） |
| `kind` | text | NOT NULL | `tip`\|`order`\|`gift`\|`payment`\|`refund` |

## 7. 范式校验

逐表过一遍。**标 ⚠️ 的是有意的反范式，都给了业务理由。**

| 表 | 1NF（原子） | 2NF（围绕主对象） | 3NF（无传递依赖） | 结论 |
|---|---|---|---|---|
| `users` | ✅ | ✅ | ✅ | 标准 |
| `persons` | ⚠️ JSON 存多值 | ✅ | ✅ | 见下 |
| `relationships` | ⚠️ JSON 存多值 | ✅ | ✅ | 见下 |
| `raw_inputs` | ✅ | ✅ | ✅ | 标准 |
| `chat_segments` | ✅ | ✅ | ✅ | 标准 |
| `facts` | ✅ | ✅ | ✅ | 标准 |
| `tags` | ✅ | ✅ | ⚠️ 派生冗余 | 见下 |
| `ledger` | ✅ | ✅ | ✅ | 标准 |
| `events` | ✅ | ✅ | ✅ | 标准 |
| `reminders` | ✅ | ✅ | ⚠️ payload 快照 | 见下 |
| `todos` | ✅ | ✅ | ⚠️ ai_reason 冗余 | 见下 |

### 7.1 反范式清单（每条都给理由）

**① `persons.platform_ids` / `contact` / `aliases` 用 JSONB**

- **违反**：1NF（字段不是原子值）
- **理由**：这些是多值属性，且**几乎不参与查询**——你不会按"抖音号 138xxx"搜人。拆成 `person_contacts` 表，每次读档案要多两次 join，收益为零
- **代价**：JSON 内部字段没法加唯一约束，去重靠应用层
- **补救**：给 JSONB 建 GIN 索引，需要时仍可查询

**② `relationships.total_in` / `total_out` 冗余累计**

- **违反**：3NF（可从 `ledger` 求和得出）
- **理由**：人列表页每个人都要显示这两个数，18 个人就是 18 次 `SUM()` 聚合。虽然量小，但这是**最高频的查询**，且数据只在写 `ledger` 时变
- **代价**：`ledger` 增删改时必须同步更新这两个字段。用**数据库触发器**保证一致性，不靠应用层记得
- **补救**：提供 `recalculate_relationship_totals(person_id)` 函数，出错可重算

**③ `tags` 整张表**

- **违反**：3NF（完全可从 `facts` 派生）
- **理由**：筛选"谁喜欢茶"要 `WHERE key='preference' AND value='白茶'`。如果每次从 `facts` 里做全文匹配，**必须扫全表 + 解析中文句子**，18 个人也要几百毫秒，而且召回不准（"白茶"可能写成"喝白茶"）
- **代价**：`facts` 变更时要同步重算 `tags`，可能出现不一致
- **补救**：`tags` 可随时全量重建（`rebuild_tags(user_id)`），这是它比 `facts` 低一级的证明——**派生表允许丢失**

**④ `reminders.payload` 存生成好的完整内容**

- **违反**：3NF（内容是档案 + 知识库的派生）
- **理由**：推送出去的文案必须**不可变**。否则你后来改了档案，回看历史提醒会发现"当时不是这么说的"，审计就废了
- **代价**：存储冗余
- **补救**：无。这是**故意保留的快照**

**⑤ `todos.ai_reason` 存 AI 生成理由**

- **违反**：3NF（理由可从上下文推导）
- **理由**：AI 生成任务时的理由依赖"当时的对话内容"，事后推导不出来。存下来是**解释性证据**，对应产品原则"建议必须带依据"
- **代价**：几乎为零（一个 text 字段）

**⑥ `chat_segments.person_id` / `reminders.person_id` 冗余**

- **违反**：3NF（可通过 `raw_input_id` / `event_id` 间接得到）
- **理由**：检索时按人查是最常见操作。不冗余就要 join 两跳
- **代价**：归属变更时要同步两边
- **补救**：归属变更只发生在确认队列里，一个地方统一处理

### 7.2 特别说明：`persons` 与 `relationships` 拆表是否违反 2NF

2NF 要求"字段围绕当前表的主对象"。

- `persons` 的主对象 = **这个人是谁**（昵称、平台号、联系方式）
- `relationships` 的主对象 = **我跟他的关系**（阶段、温度、金额、预算）

如果合并，`persons` 表里就会同时装两个主对象的信息，**反而违反 2NF**。
所以拆开不是为了好看，是**为了符合范式**。

## 8. 多用户隔离（RLS）

### 8.1 四层防护

| 层 | 做法 |
|---|---|
| **表结构** | 每张业务表 `user_id NOT NULL` + 外键 |
| **数据库** | RLS 策略强制 `user_id = current_setting('app.user_id')::bigint` |
| **应用** | 每个请求开头 `SET LOCAL app.user_id = ?` |
| **文件** | `data/uploads/{user_id}/...` |

### 8.2 需要开启 RLS 的表

`persons`、`relationships`、`raw_inputs`、`chat_segments`、`facts`、`tags`、`ledger`、`events`、`reminders`、`todos`、`extraction_logs`、`temperature_snapshots`、`vector_chunks`

**`users` 表不开 RLS**——登录时还没确定用户身份，靠应用层按 `username` 查。

### 8.3 策略写法

```sql
ALTER TABLE persons ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON persons
  USING (user_id = current_setting('app.user_id')::bigint)
  WITH CHECK (user_id = current_setting('app.user_id')::bigint);
```

> ⚠️ `WITH CHECK` 不能漏——只写 `USING` 的话，**插入时可以伪造别人的 user_id**。
>
> ⚠️ 应用连接必须用普通角色 `keeper_app`，**不能用 `postgres` 超级用户**，超级用户默认绕过 RLS。

## 10. 删除策略（级联图）

用户明确要求"**全删，不留痕**"。所以：

```
删 persons（王姐）
  ├─ CASCADE → relationships        （关系）
  ├─ CASCADE → facts                （事实）
  ├─ CASCADE → tags                 （标签）
  ├─ CASCADE → ledger               （往来）
  ├─ CASCADE → events               （事件）
  ├─ CASCADE → reminders            （提醒）
  ├─ CASCADE → raw_inputs           （截图原图）
  ├─ CASCADE → chat_segments        （对话片段）
  ├─ CASCADE → temperature_snapshots
  ├─ CASCADE → vector_chunks
  └─ SET NULL → todos               ← 唯一例外：任务留着，只是不挂人
```

**还要手动做两件事**（数据库管不到）：

1. **删文件**：`data/uploads/{user_id}/{raw_input_id}.*` 要真删
2. **删向量**：`vector_chunks` 里该人的 embedding 随 CASCADE 删掉（V2）

**删用户的级联**：`users` 被删 → `persons` CASCADE → 上面整棵树全删。**但 `users` 表本身不轻易删**，禁用用 `is_active=false`。

## 12. 验收标准

按方法论"先跑通基础结构即可，不要一口气写完整业务"。

### 12.1 必须通过的四项

| # | 验收 | 怎么做 |
|---|---|---|
| 1 | **能连接** | `psql` 用 `keeper_app` 角色连上库 |
| 2 | **核心表能创建** | `alembic upgrade head` 无报错，15 张表都在 |
| 3 | **Migration 能回滚** | `alembic downgrade -1` 再 `upgrade head`，不报错 |
| 4 | **能增删查** | 建一个 user → 一个人 → 一条事实 → 查出来 → 删人 → 关联数据全没了 |

### 12.2 RLS 专项验收（最关键）

```
① 用账号 A 登录，建一个人「测试A」
② 用账号 B 登录，建一个人「测试B」
③ A 查列表 → 只能看到「测试A」
④ A 直接用 B 的 person_id 查详情 → 返回 404，不是报错
⑤ A 尝试 INSERT 一个 user_id = B 的记录 → 被数据库拒绝
```

第 ⑤ 条是 `WITH CHECK` 的验证，**最容易漏**。

### 12.3 每个字段都要能回答"为什么存在"

建表前逐个过一遍：解释不了用途的字段，删掉。

### 12.4 提交时机

跑通 12.1 的四项 → **立刻 git commit** → 再开始写接口。


**已有的图不自动删**。提供手动「清理历史原图」（二次确认 + 明确告知将失去什么）。

**为什么默认永久保留**：因为「出处」是这个产品的信任基础。一条没有原图可查的建议，用户不敢信，整个确认机制就废了。

### 13.2 被否定的事实：保留，但不参与任何计算

**字段**：`facts.status = 'rejected'`

**规则**：

| 用途 | 是否参与 |
|---|---|
| 画像综述 | ❌ |
| 标签派生 | ❌ |
| 提醒建议 | ❌ |
| 档案页展示 | ❌（除非开"显示已驳回"） |
| **抽取准确率统计** | ✅ |

**为什么保留**：用户点 ✗ 等于免费给了一次人工标注。这是半自动（HITL）机制唯一的回报来源——**丢掉的不是数据，是改进模型的机会**。

### 13.3 导出：做，同步生成

**接口**：`GET /api/export` → 直接返回 ZIP

```
export-20261027.zip
├── person-019-王姐/
│   ├── profile.json      # 档案 + 关系 + 标签
│   ├── facts.json        # 全部事实（含来源与置信度）
│   ├── ledger.csv        # 往来账（Excel 可直接打开）
│   ├── timeline.json     # 时间线
│   └── images/           # 原始截图
├── person-020-张总/
└── README.md             # 说明这份数据是什么、怎么读
```

**不上异步**：18 个人的数据同步打包几秒钟，做任务队列是浪费。

**为什么导出是必须的**：整套系统的承诺是"你的数据你做主"。不能只承诺删除，不提供带走。

### 13.4 手动新建人：支持

`persons` 不依赖 `raw_inputs`，提供 `POST /api/persons`。

**场景**：刚加微信还没聊过、补录老客户、从别处导入。

**必填只有 `nickname`**，其余全可空——**先建个空壳，后面投喂慢慢长**。这符合"人只做投喂和查看"，不该因为建档而填十个字段。
