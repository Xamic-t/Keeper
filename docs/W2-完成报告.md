## 三个真实撞上的坑（这才是本周的收获）

### 坑 1 · `SET LOCAL app.user_id = :uid` 根本跑不起来

Postgres 的 `SET` 语句**不接受绑定参数**，SQL 层直接报 `syntax error at or near "$1"`。
W1 写这行时没有业务路由，所以从没被执行过；W2 第一个业务接口就炸了。

**改法**：`SELECT set_config('app.user_id', :uid, true)`——参数化的 `SET LOCAL`，
第三个参数 `true` 就是"事务级"。

### 坑 2 · 事务级变量会被 `commit()` 顺手带走

`is_local=true` 的变量活不过事务。service 里 `commit()` 之后，同一 session 再查库就会拿到
空字符串，Postgres 报 `invalid input syntax for type bigint: ""`——报错信息完全看不出根因。

**改法**：在 `db.py` 挂 SQLAlchemy 的 `after_begin` 事件，每个新事务开头自动补一次
（`session.info["rls_user_id"]`）。调用方只需要登记"这次请求属于谁"，
不用再记"提交后不能查库"这种隐性规矩。ARCHITECTURE 15.2 已同步改写。

### 坑 3 · Starlette 发完 500 还会再抛一次

兜底中间件把响应发出去之后会 `raise` 原异常（给服务器记账用）。真实服务器会吞掉，
`httpx.ASGITransport` 默认会把异常抛回测试代码。所以测 500 的用例必须
`raise_app_exceptions=False`，否则永远测不到那个响应。
