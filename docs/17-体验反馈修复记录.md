## 二、逐条记录

### F1 · 确认页点一条，整组顺序乱跳

**用户原话**

> 它排列是孟亚男、小赵快乐小居、然后小包老师，我点了孟亚男的一个之后，直接把快乐小居顶上来，孟亚男到后面去了。我每点一个，它就会跳这个排列。

**根因**（`backend/app/services/confirm.py`）

```python
# 旧代码
.order_by(Fact.confidence.asc(), Fact.created_at.desc())   # 全局按置信度排
...
grouped: dict[int, ConfirmationGroup] = {}                  # 再按人分组
```

组的先后顺序，依赖「谁那组里有**最低分**的条目」。孟雅楠有一条 0.5 分的，被点掉后她那组的最低分变成 0.85，位置自然变化。**这是排序逻辑的错误用法：先排序再分组，等于让分组顺序被单条记录绑架。**

前端还有一层放大器：每点一次都 `await load()` 整页重拉，所以后端顺序一变，屏幕上立刻重排。

**修复**

- 后端：先分组 → 组内按 `(confidence, -created_at)` 排 → 组间按「组内最新一条 created_at」排，待定组固定第一
- 前端（`ConfirmView.vue`）：新增 `dropItem()`，处理完**只在本地点掉那张卡片，不再重拉列表**

**为什么前端也要改**：后端的排序只要不是绝对稳定（比如同一人不同批次的事实时间不同），重拉就会跳。**列表页操作完就 reload 是偷懒写法**，这条记进项目约定。

**验证**：`list_confirmations` 前后对比，点掉一条后组顺序不变；`pytest` 106 通过。

### F2 · 投喂列表全显示「截图」

**用户原话**

> 这三张截图名字都叫截图，你名字要不给我叫文件原名，要不就给我叫时间。后面不用给它打个 tag 已识别，你后面可以给我打个查看原图，或者直接给缩略图。

**根因**

`raw_inputs` 表**根本没有文件名字段**（`backend/app/models/input.py`）。上传时 `UploadItem.filename` 只用于返回给调用方，从不落库。前端拿不到名字，只能按 `kind` 显示"截图"。

**修复**

| 层 | 改动 |
|---|---|
| 迁移 | `0005_raw_input_filename.py` 加 `original_filename varchar(255)` |
| 模型 | `RawInput.original_filename` |
| 服务 | `ingest_images()` 落库时写入（截断 255）；文本投喂留空 |
| 接口 | `RawInputOut.original_filename` |
| 前端 | 缩略图（`/api/raw-inputs/{id}/file`）+ 文件名；无名字退化成「截图 今天 18:01」；去掉「已识别」tag，只保留 pending/processing/failed 提示 |

**验证**：列表接口返回 `IMG_8521.PNG / IMG_8523.PNG / IMG_8522.PNG`，缩略图接口 200 且字节数与本地文件一致。

### F3 · 今日页不是能勾选的待办清单

**用户原话**

> 这里什么更新哥姐动态、复盘今日数据，前面都给我做成这种 ToDoList，完成了就点个勾。ToDoList 你做不来吗？你至少要把 ToDoList 给我还原成一个完整的吧。

**根因（两处）**

1. `today.py` 里 `TASK_LIMIT = 3` —— 设计初衷是"一屏别塞太多"（避免制造焦虑），但实现成了**只返回 3 条**，第 4 条以后直接不给。用户看到的"该做的事"是不完整的。
2. 「提醒」类型只能"转待办"，没有"完成"这个动作。转待办要跳一次、再勾一次，两下才等于一下。

**修复**

| 层 | 改动 |
|---|---|
| 后端 | `TASK_LIMIT` 3 → 20；新增 `POST /reminders/{id}/done`（status → `clicked`，幂等） |
| 服务 | `reminder.mark_done()` |
| 前端 | 重做成标准 ToDoList：圆形勾选框、勾完划线置灰沉到「已完成」、待办可取消（改回 `open`，提醒不可逆） |

**设计取舍**：提醒勾掉是**不可逆**的（后端只有 `clicked`，没有回滚接口），所以完成态不再给取消入口；待办可以反悔。

**验证**：今日页从 3 条变成返回全部；勾选后 `status` 落库；取消勾选恢复 `open`。

### F5 · 时间线只有年月日

**用户原话**

> 时间线，人物 profile 的时间线给我加上。准确的小时分钟，不只是这个年月日。

**根因（两层）**

1. `TimelineItem.day` 是 `date` 类型，`build_timeline()` 里三处都取 `.date()` / 直接用 `date` 字段 —— 结构上就没有时分。
2. **更深一层**：改完格式后发现显示的是「今天 18:01」，即**投喂入库时间**，不是聊天发生时间。查 `chat_segments.said_at`，全是 `null`。

追下去发现：`prompts/v1_extract.md` 里有 `said_at` 这个字段，但**从没写怎么取**。模型看到没规则，一律返回 `null`。

**修复**

| 层 | 改动 |
|---|---|
| 接口 | `TimelineItem.day(date)` → `at(datetime)` + `precision("minute"/"day")` |
| 服务 | 事实优先取 `chat_segments.said_at`（批量一次查，避免 N+1），没有才退回 `created_at`；往来/事件表里只有日期，标 `precision="day"` **不编造时分** |
| Prompt | 新建 `prompts/v2_extract.md`，明确说清 `said_at` 规则；`PROMPT_VERSION` 升 `v2` |
| 前端 | 「今天 14:32」「昨天 09:05」「9月21日 16:41」「10月28日」四档 |

**v2 prompt 新增的规则**

| 截图里看到 | 怎么填 |
|---|---|
| 消息上方有「9月21日 16:41」 | 该时间之后的几条消息都填 `2026-09-21T16:41:00+08:00` |
| 只有「昨天 21:30」 | 换算成具体日期，算不准就 `null` |
| 只有状态栏时钟（如 17:45） | **`null`** —— 那是截图时的手机时间，不是对话时间 |
| 完全没有时间信息 | **`null`** |

**验证**：用 v2 重抽 `IMG_8521`（孟雅楠，截图里有「9月21日 16:41」），落库结果为：

```
2026-09-21T16:41:00+08:00   said_at_inferred=False
```

## 四、顺带修掉的两个同源问题

用户没提，但属于同一片区域，不改会继续恶心人：

### S1 · 每日模板任务堆积

今日页里出现两条「复盘今日数据」（`due=2026-10-28` 和 `due=2026-11-01`）。`ensure_daily_template()` 每天补一份，但**从不清理昨天的**。几天不打开就会堆出十条一模一样的。

修复：生成今天模板前，把 `status=open` 且 `due_date < today` 的 template 任务置为 `dropped`。

### S2 · prompt 有字段没规则

见 F5。`said_at` 在 v1 里是个"有名字没定义"的字段，模型只能返回 null。**这类问题不会报错，只会安静地少一个维度**——以后加字段时，prompt 里必须写清取值规则和"不确定怎么填"。

## 六、经验（写进项目约定）

1. **列表页操作后不要 `await load()`**。本地更新视图，只有用户主动刷新才重拉。否则后端任何排序抖动都会变成屏幕跳动。
2. **先分组再排序，不要先排序再分组**。全局排序会让"组"的展示顺序被组内某一条绑架。
3. **数据库里没有的字段，前端不可能显示**。看到"全都显示成同一个词"，先查表结构，别改 UI。
4. **prompt 里的字段必须有取值规则**，否则模型一律给 null，且不会报错。
5. **改 prompt 必须新建 vN 文件 + 升 `PROMPT_VERSION`**，不原地改，否则历史审计不可比。
