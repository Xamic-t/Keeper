# 32 · 助理整合开发计划（2026-11-03 凌晨批次）

> 用户原话要点：**不要另开窗口、不要单独启动、不要藏在设置里**。
> 要的是：主界面一级菜单「助理」→ 一个像微信/本对话这样的聊天窗口 →
> 能发文字、能甩图片、能问问题、能一句话让它建待办/建事件。
>
> 交付标准：明早打开软件，导航栏有「助理」，点进去就能聊，聊完能看到它真的建了待办。

---

## 一、问题解剖：现在为什么难用

| 现状 | 为什么不行 |
|---|---|
| 助理是 Harness 侧车（Node 容器，3080） | 要单独 `docker compose --profile assistant up`；没起就是白屏 |
| 前端只是 iframe 嵌 dsh Web UI | 要手动粘带 `?token=` 的地址到 sessionStorage，token 每次重启都变 |
| 入口只在桌面侧栏，手机端要绕设置 | 手机上根本找不到 |
| 后端 `/api/chat` 是**规则路由**，不是模型对话 | 只做"投喂/查询"两件事，不能说"帮我建个待办" |
| 没有会话记录 | 刷新就没了，不像聊天 |

**结论**：不是"改文案"能解决的，是**入口形态 + 能力边界**两件事都要重做。
因此今晚分两块：**① 助理变成主界面的一级页面（自研聊天 UI）；② 后端给它一个真模型对话 + 动作执行能力。**

---

## 二、目标形态（做完是什么样）

```
导航：今日 · 投喂 · 助理 · 人 · 确认 · 日历 · 待办      ← 助理在第三位，桌面+手机都有

┌────────────────────────────────────────────┐
│  助理                              [清空]   │
│                                             │
│  你可以这么说：                              │
│  · 11 月 4 号王姐生日，帮我建个待办           │
│  · 王姐喜欢什么？                            │
│  · 这张截图里的人说了啥（附图）              │
│                                             │
│                    王姐生日那天要送什么？ ┃  │
│         ┌──────────────────────────────┐    │
│         │ 她 3 月买过白茶（依据：对话原文） │  │
│         │ 预算 300-500，别送烟              │  │
│         └──────────────────────────────┘    │
│  ┌──────────────────────────────┐           │
│  │ 好，11-04 给王姐建了待办：     │           │
│  │ 准备生日礼物                   │           │
│  │ ✅ 已创建待办 · 查看            │           │
│  └──────────────────────────────┘           │
│                                             │
│  [📎] 说点什么…                      [发送]  │
└────────────────────────────────────────────┘
```

**四条硬要求**：
1. 一级菜单，桌面 + 手机都可见，不需要任何额外启动；
2. 消息进去 → 模型回，带**打字中**状态，失败可重试（不静默丢）；
3. 支持附图：图走既有 ingest + 抽取流水线，抽出来的东西进对话上下文；
4. 能执行动作：**建待办 / 建事件（生日、结款、自定义）/ 记一条待确认事实**，
   执行完在气泡下方显示"已创建 · 查看"，点了能跳过去。

## 三、技术方案（为什么这么选）

| 决策 | 选择 | 理由 |
|---|---|---|
| 模型调用 | 复用 `VisionClient`，新增 `converse(messages)` | 主备双通道、超时重试、Key 校验都已经在里面；再引一个 SDK 等于两套失败语义 |
| 工具调用形态 | **JSON 协议**（prompt 约定 `{reply, actions[]}`），不用 OpenAI function-calling | 主备两个通道对 tools 支持不一致；JSON 协议两边都稳，且能被现有 `parse_json` 校验 |
| 会话存储 | 新表 `chat_messages`（RLS 同其它表） | 刷新不丢、能"清空重来"；存 DB 才符合"业务真相只在 Postgres" |
| 写档案 | `add_fact` 只落 **pending**，进确认页 | ARCHITECTURE 铁律：AI 不许直接写档案 |
| Harness 侧车 | **降级为可选、默认不启**，前端不再依赖 | 用户明确不要"另开窗口"；侧车保留给以后做 agent 实验，删了不影响助理 |
| 老 `/api/chat` | 保留不动（投喂页的"对话式投喂"还在用） | 不破坏既有验收与 e2e；新助理走新接口 |

**动作白名单（V1，最多 3 个/轮）**

| type | 参数 | 落到哪 |
|---|---|---|
| `create_todo` | `title` `due_on?` `person?` | `todos` 表 |
| `create_event` | `event_type` `title` `occurs_on` `person?` | `events` 表（生日/结款/自定义/节日） |
| `add_fact` | `person` `content` `category` | `facts` 表，`status=pending` |

> 不做：删除、改别人的数据、批量导入。破坏性动作不进白名单——模型判断错一次就够用户受的。

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| 模型不按 JSON 回 | 已有 `parse_json` 直接 502；前端可重试；prompt 里给正例 |
| 模型瞎建待办 | 只允许 3 条/轮、破坏性动作不进白名单、建完在气泡里明示"已创建"可撤销（去待办页删） |
| 附图慢（抽取 3–8 秒） | 前端先上"正在看图…"，超时 60 秒；失败保留原消息可重试 |
| 上下文太长 | 只带最近 8 轮 + 快照；不做全量历史 |
| 和 `/api/chat` 混淆 | 两个接口职责写进 docs/07：`/chat` = 投喂对话，`/conversation` = 助理对话 |
