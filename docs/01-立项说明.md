# 01 · 立项说明

> **项目工作名**：知人（暂定，可改）  
> **毕设题目**：基于大语言模型的私域客户画像构建及需求感知提醒系统研发  
> **文档版本**：v1.0 · 2026-10-27  
> **状态**：已完成 11 轮需求对齐，本文为对齐结论。后续变更需在文末变更记录中登记。

---

## 1. 一句话

**把你脑子里的「人」搬进系统：你只负责投喂原始材料，系统替你记住、替你判断、在你该出手的时候推你一把。**

给评委的正式表述：

> 一个面向私域关系维护场景的 LLM Agent 系统。用户只提供非结构化原始材料（聊天截图、一句话），系统完成多模态信息抽取、双层画像构建、关系状态建模与主动式需求感知提醒，把"人记忆并维护关系"迁移为"系统记忆并提醒人"。

---

## 2. 要解决的问题

### 2.1 三个具体困境（不是一个）

很多人会把这件事说成"记不住"，但它其实是三个层次不同的问题，且难度递增：

| 层次             | 困境     | 表现                                  | 本质       |
| -------------- | ------ | ----------------------------------- | -------- |
| **L1 记不住**     | 认知带宽不够 | 几十个人，谁喜欢什么、家里什么情况、上次聊到哪儿，全在脑子里      | 存储问题     |
| **L2 想不起**     | 信息沉底   | 微信、抖音两头聊，聊完就沉了；见面前想翻记录，翻半天          | 检索问题     |
| **L3 不知道该干什么** | 没有判断力  | 谁该问候、谁该送礼、谁该先别打扰——靠脑子和备忘录，备忘录不会主动找你 | **决策问题** |

**市面上所有工具只解决 L1 和 L2**（CRM、备忘录、微信备注），L3 是空的。而 L3 才是"关系维护"真正的成本所在——**你缺的不是资料，是判断**。

### 2.2 现有工具为什么不行

它们共同的假设是：**信息必须先被整理成结构，才能进系统。**

- CRM 让你填表、选下拉框、打标签
- 备忘录让你自己写清楚
- 微信备注只能存一行字

而你手里真实的材料是：**一堆截图，和一句"陈姐家猫生病了"。**

你最缺的恰恰是"整理"这一步。所以要求你整理的工具体系，从入口就错了。

> **要解决的不是"给我一个数据库"，是"让系统去适配我随手丢进去的东西"。**

### 2.3 一个被忽略的问题：不是"记什么"，是"什么时候该做什么"

传统工具的时间轴是"过去"——记录已经发生的事。

但关系维护真正的动作发生在**未来**：什么时候该联系、什么时候该送礼、什么时候**不该打扰**。

最后这半句是原方案没有的，也是本项目的核心增量：

> **知道什么时候不打扰，比知道什么时候打扰更难，也更值钱。**

## 3. 目标用户

三层，从窄到宽。**产品按 L1 做深，机制按 L3 设计。**

| 层级     | 用户                                      | 规模  | 本项目的角色                   |
| ------ | --------------------------------------- | --- | ------------------------ |
| **L1** | 本人（主播 + 私域经营，哥姐同时是客户）                   | 1 人 | MVP 唯一真实用户，所有设计以他的真实习惯为准 |
| **L2** | 同类主播 / 小主播 / 私域小卖家                      | 中等  | 第一个可复制的行业包（主播版）          |
| **L3** | 销售、保险、医美顾问、房产中介、小微老板——**任何需要长期维护一批人的人** | 大   | 机制泛化的目标，不是 MVP 范围        |

### 3.1 L1 用户的关键特征（决定了产品形态）

1. **哥姐就是客户**——同一个人身上同时存在打赏关系和交易关系，且两种关系的时间线是交织的
2. **维护规模 20 人以内**，但会自然更替：新的人进来，旧的人沉底
3. **推送只服务最近活跃的 20 人**——超出这个窗口的人不打扰，档案仍在
4. **主战场是聊天截图**，80% 的有用信息来自一对一私聊
5. **截图在手机上**——所以投喂链路必须手机优先

> **20 这个数字不是随便定的。** 它是人的社交带宽上限（邓巴数的小圈子层）。这意味着产品要做的是"帮一个人管好他的核心圈子"，不是"帮一个公司管好一万个客户"。这个定位差异，决定了后面所有取舍。

## 4. 核心机制

五个环节，一句话概括：

```
投喂  →  抽取  →  画像  →  感知  →  提醒
 ↑                                      │
 └──────────── 用户只做两件事 ───────────┘
```

| 环节          | 谁做    | 产出                              |
| ----------- | ----- | ------------------------------- |
| **投喂**      | **人** | 截图 / 一句话 / 手动补录                 |
| **抽取**      | AI    | 事实、事件、往来记录、需求信号，带置信度与出处         |
| **画像**      | AI    | 分层画像：一段自动重写的综述 + 一套可筛选的标签       |
| **感知**      | AI    | 关系温度（状态）+ 场景信号（时机）→ 该不该出手、出手干什么 |
| **提醒**      | AI    | 带依据的建议 + 可直接用的话术，推到企业微信         |
| **确认 / 查看** | **人** | 点 ✓ / ✗，或打开档案读一遍                |

**人只做两件事：投喂，和查看。** 这是产品的第一原则，任何要求用户"先整理再录入"的设计都是失败的。

## 5. 价值判断

### 5.1 学术价值（支撑毕设）

| 价值点            | 为什么能立住                                                 |
| -------------- | ------------------------------------------------------ |
| **范式差异可论证**    | "系统适配人"vs"人适配系统"不是口号，可以用同一批任务的**录入耗时**和**信息完整度**做对比实验  |
| **三个技术支点都有实现** | 多模态抽取 Pipeline、混合检索路由、主动式 Agent——每一个都能对应到具体代码和可展示的中间产物 |
| **可解释性有物证**    | `extraction_logs` / `agent_runs` 两张表，答辩可现场调出任意一条记录逐字段讲 |
| **有对比实验**      | 纯 RAG vs 混合路由、全自动 vs 半自动确认，都是可量化的                      |

### 5.2 产品价值（支撑长期）

| 价值点         | 说明                         |
| ----------- | -------------------------- |
| **刚需且高频**   | 漏一个生日 = 关系受损；漏一笔回款 = 真金白银  |
| **现有方案真空**  | CRM 太重、备忘录太笨、微信备注太浅，中间没有东西 |
| **垂类可复制**   | 主播 → 销售 → 顾问型职业，机制完全复用     |
| **数据主权是卖点** | 部署在自己的服务器，客户名单不经过第三方 SaaS  |

### 5.3 不成立的风险（诚实地说）

- 如果**抽取准确率低于某个阈值**，用户会失去信任并弃用——这是最大风险，见 `04` 的风险章节
- 如果**投喂成本高于收益**，用户会在两周内停止使用——所以"手机端一键投喂"是生死线
- 如果**提醒误报率高**，用户会关掉推送——所以温度设计必须保守

## 6. 爆点与差异点

按"能不能被一句话讲清楚"排序，前三条是核心。

### 6.1 差异点一：不是记录系统，是判断系统

**所有关系管理工具都在回答"他是什么样的人"，本系统回答"我现在该做什么"。**

同样是"王姐生日还有 3 天"：

- 传统工具：到点弹一个提醒
- 本系统：**该下单了 → 建议茶叶礼盒（300-500）→ 因为她 10-03 说过喜欢喝茶，去年送的是香水不重复 → 附一段可直接复制的话术**

差别不在功能，在**从数据到行动的那一跳**。

### 6.2 差异点二：需求感知 = 温度 × 场景（知道什么时候不打扰）

这是本项目的理论内核，也是最能讲的一页。

单看"关系温度"会误判，单看"生活场景"没有优先级，两者叠起来才成立：

|                                    | 温度在升               | 温度在降                   |
| ---------------------------------- | ------------------ | ---------------------- |
| **有明确场景信号**<br />（孩子高考／装修／生病／想买东西） | **成交或升温的时机** → 该出手 | **他在忙、遇上事了** → 别打扰，先记着 |
| **没有场景信号**                         | 正常维护 → 按节奏走        | 可能真凉了 → 该去关心一句         |

**右上角那一格是这个系统最有价值的地方。** 一个只知道"该联系谁"的系统是骚扰机器；一个知道"这时候别找他"的系统才是伙伴。

传统 CRM 永远做不到这一格，因为它没有"场景"这个维度——它只有标签和商机阶段。

### 6.3 差异点三：会过期的记忆（记忆半衰期）

AI 抽取的事实不是永久的。"她孩子在高考"这句话，一年后就是错的；"她最近在装修"，三个月后就失效了。

所以每条事实都带**半衰期**，过期自动降权、提示复确认：

| 信息类型           | 半衰期     | 处理            |
| -------------- | ------- | ------------- |
| 生日 / 纪念日       | 永久      | 无需复确认         |
| 禁忌 / 雷区        | 1 年以上   | 每年生日前顺带确认     |
| 家庭结构 / 职业      | 6-12 个月 | 有新信息即更新       |
| 偏好（吃穿用度）       | 约 6 个月  | 同上            |
| 近期动态（装修/搬家/出差） | 1-3 个月  | 过期降权，不再作为建议依据 |
| 情绪状态           | 1-2 周   | 过期失效          |

**这是"动态画像"和"静态标签"的根本区别**，也是论文里画像构建那一章的核心论点：传统画像的标签是死的，本系统的画像是会呼吸的。

### 6.4 差异点四：混合检索路由（RAG 的边界）

系统里有四种"想不起来"，但只有两种该用 RAG：

| 类型   | 例子                    | 方案               |
| ---- | --------------------- | ---------------- |
| 精确事实 | 王姐生日几号？消费档？           | **SQL**          |
| 跨人筛选 | 哪些哥姐喜欢茶？谁快过生日？        | **SQL**（标签 + 日期） |
| 模糊回忆 | 她上次提的她闺女那事是啥来着？       | **RAG 记忆层**      |
| 知识增强 | 她 40 岁、爱喝茶、预算 500，送啥？ | **RAG 知识层**      |

> "我知道 RAG 的边界在哪"比"我全用 RAG"高级得多。而且这个边界可以用对比实验量化。

### 6.5 差异点五：数据主权

部署在自己的服务器，客户名单、聊天记录、消费金额不经过任何第三方 SaaS。

对做私域的人是真实痛点——**他们的客户名单就是全部身家**。

## 7. 边界：明确不做的事

边界比功能更重要。以下每一条都是主动放弃，且放弃的理由要能说服评委。

| 不做                   | 为什么                                            |
| -------------------- | ---------------------------------------------- |
| **自动抓取微信/抖音聊天**      | 个人号自动化违反平台协议，2026 年明令禁止，可封号。只做手动截图上传           |
| **全自动归档（AI 抽完直接落库）** | 抽错了你不知道。生日、金额、禁忌抽错的代价是送错礼、说错话——比没有系统更糟         |
| **AI 替我聊天**          | 它只帮我记和提醒，跟人说话的还是我。这条是产品伦理底线                    |
| **多端原生 App / 小程序**   | 响应式 Web + PWA 添加到主屏就够，一个人做不起三端                 |
| **团队协作（多人共享同一批客户）** | 这是个人工具，不是团队 CRM。**"多用户"指的是每人一个独立空间**，不是多人共享一个客户库——后者要组织架构、成员权限、审批流，是另一个产品 |
| **做平台 / 做社区 / 做流量**  | 一个极度锋利的个人工具，比一个平庸的平台有价值                        |
| **实时监听直播弹幕并即时反应**    | 弹幕数据可作补充输入，但"直播中实时干预"是另一个产品，会毁掉注意力             |

## 8. 三条不可妥协的原则

任何时候要砍功能，砍别的也不能砍这三条。

### 原则一：人只做两件事——投喂和查看

任何要求用户"先整理好再录入"的设计都是失败的。截图、一句话、语音转文字，随便什么形式，系统都得吃下去。

**推论**：如果某个功能需要用户每天多花 5 分钟整理，它的价值必须大到能抵过这 5 分钟，否则不做。

### 原则二：AI 的建议必须带依据

"建议送茶叶"是废话；"因为她 10-03 说过喜欢喝茶、去年送过香水所以不重复，建议送茶叶"才有用。

**推论**：没有出处、没有推理链的建议，宁可不出。这条直接决定了 V1 必须做 AI 建议，不能只推一条干巴巴的日期。

### 原则三：不确定的交给人，AI 不许硬猜

生日、金额、禁忌这类抽错代价高的，宁可多问一句，也不能自作主张写进档案。

**唯一例外**：待办。待办错了顶多是一条废任务，删掉就行，所以待办可以直接进列表，不打扰用户。

## 9. 立项结论

| 项      | 结论                                 |
| ------ | ---------------------------------- |
| 项目类型   | 双轨：毕业设计 + 个人工具产品，同一套代码             |
| MVP 定位 | **记忆系统**（投喂 → 画像 → 日期驱动提醒 + AI 建议） |
| 二期定位   | **判断系统**（关系温度 → 需求感知 → 状态驱动提醒）     |
| 主数据链路  | 聊天截图（多模态抽取）                        |
| 技术身份   | 多模态信息抽取系统，不是 CRM                   |
| 部署形态   | 自建服务器，手机优先                         |
| 成功标准   | 见 `04-计划与验收.md`                    |
