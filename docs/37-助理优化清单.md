# 37 · 助理（原 Harness）优化清单

> 2026-11-03 16:30。用户要的是：**Prompt 能在哪优化、工具能在哪优化、流程能在哪优化、
> 工具调用能不能显示在对话框里**。

---

## 0. 先把一件事说清楚：现在没有 Harness 了

昨晚你说"不要另开窗口、不要单独启动"，我把 Harness 侧车（`dsh`，Node 容器）整个撤了，
助理改成主服务里的原生对话。所以**现在没有"Harness 流程"可优化**——但它原来的职责
（编排、工具调用、会话）现在由我们自己这一段承担：

```
用户消息
  → build_snapshot()        今天 / 人物（每人 3 条事实 + 3 个标签）/ 7 天内事件 / 今日待办
  → render_prompt()         prompts/v1_assistant.md + 快照
  → build_messages()        system + 最近 8 轮 + 本轮
  → vision.converse()       关思考、不开 response_format、末尾加 JSON 硬约束、2 次重试
  → parse_json()            原样 → 剥围栏 → 括号定位
  → execute_actions()       白名单 3 个动作，一轮最多 3 个
  → 落库 chat_messages
```

要"真编排"，有两条路：

| 方案 | 代价 | 我的建议 |
|---|---|---|
| A. 把编排做在主服务（工具注册表 + 多步循环） | 自己写循环，但写操作天然过 RLS / 确认队列 | **推荐** |
| B. 重新接 Harness 当编排层 | 又把"另起服务"装回来；它要写数据得开写接口，破坏 19.7.4 的前提 | 不建议 |

下面所有优化按 A 走。

## 一、Prompt 能在哪优化（6 条，按收益排序）

现状：`backend/prompts/v1_assistant.md` 一个文件同时干四件事——人设、能力、动作协议、资料。
**实测证据**：只靠 system 里的格式要求，模型 5/5 回散文，必须靠末尾补一句"只输出 JSON"才稳。
这说明"一份 prompt 什么都管"已经开始互相稀释了。

| # | 问题（现在） | 怎么改 | 收益 |
|---|---|---|---|
| P1 | 格式要求被人设/资料稀释，得靠代码补一句 nudge | **拆三段**：`system_identity.md`（人设+语气，≤10 行）/ `tool_protocol.md`（字段表+3 个 few-shot）/ 数据快照。代码按段拼 | 格式稳定性↑，且能单独迭代某一段 |
| P2 | 只有一个"动作形状"示例，没有"什么时候该做"的正反例 | 加 3 正 1 负 few-shot：①纯问答→空动作 ②"11 月 4 号王姐生日"→建事件+待办 ③信息不足→反问 ④**用户只回"嗯"→空动作** | 误建/漏建都会降 |
| P3 | 日期换算规则只在注释里提了一句 | 明确写：`今天` 取快照字段；"明天/后天/下周X"按今天推算；**只输出 YYYY-MM-DD** | 少一批"日期看不懂"的失败 |
| P4 | 没约束"引用事实不许改写" | 加一条：reply 里引用事实必须原样，不得扩写/换词 | 防"喜欢白茶"被说成"爱喝绿茶"（这类错误最难发现） |
| P5 | 语气只有"简短"两个字 | 写成可判定：≤3 句、不以"好的/没问题/当然"开头、不用"您好" | 现在模型仍会说"好的，我帮你建……" |
| P6 | prompt 版本没记录 | `PROMPT_VERSION` 只用于文件名；把版本写进每轮日志（或 messages.actions.meta） | 以后 A/B 能归因，不然改了不知道好坏 |

**怎么做 A/B**：准备 20 条固定输入（问答 8 / 建待办 4 / 建事件 4 / 记事实 2 / 边界 2），
每条跑 5 次统计"JSON 合规率 / 动作正确率 / 回复准确率"。改 prompt 前后各跑一遍——这就是对比实验的雏形。

## 二、工具能在哪优化（5 条）

现状：白名单 3 个 —— `create_todo` / `create_event` / `add_fact`（只落 pending）。
一轮最多 3 个；纯应答词（嗯/好/收到）机器侧拦截不执行。

| # | 问题 | 怎么改 | 为什么值得做 |
|---|---|---|---|
| T1 | **口述收付款记不进往来** | 加 `create_ledger`（direction/amount/kind/occurred_on/person） | 现在说"收了 800 样品费"只会进 `add_fact` 待确认，**往来页看不到、画像算不出**，这是真缺口 |
| T2 | 人名只能精确匹配昵称/别名 | 精确 → 别名包含 → LIKE 模糊，返回**候选列表**让模型反问 | "王姐" 匹配不到 "王姐（抖音）" 这类 |
| T3 | 工具结果只有一句人话 | 结果改成结构化：`{name, args, ok, result, ms, candidates}` | 这是"把工具调用显示在对话框里"的前提（见第四节） |
| T4 | 重发同一句话会建两条待办 | 幂等键：`hash(user, text, tool, args)` + 10 分钟窗口 | 双开标签页、手抖重发都会踩 |
| T5 | 失败原因不可行动 | reason 带上候选/正确字段名（"没认出人，候选：王姐、王姐（抖音）"） | 用户能直接改一句话重试，而不是干瞪眼 |

**不建议现在加的工具**：删除、批量导入、改别人数据。破坏性动作进白名单前，必须先有"确认队列"（见 F2）。

## 三、流程能在哪优化（7 条）

| # | 现状 | 怎么改 | 影响 |
|---|---|---|---|
| **F1** | 单轮：一次模型 → 直接执行动作 | **多步**：允许模型先调只读工具（search_person / read_facts），拿到结果再决定 → 最多 2 跳 | 从"背名单猜"变成"查了再答"，这是 agent 与一次性 JSON 的分界 |
| **F2** | 写操作一步到位，建错了要去删 | **轻确认**：建事件 / 记事实先给预演（"要建：11-04 王姐生日，确认？"），点确认才落库；建待办可直接做 | 错误成本从"去删一条"降到"点一下取消" |
| **F3** | 同步等 1–6 秒，界面只有"正在想…" | **SSE 流式**：先出文字，再出"正在查/正在建" | 体感差别最大的一条 |
| **F4** | 上下文固定：8 轮 + 每人 3 条事实 | **按提及的人动态加载**：提到王姐就多给她 5 条事实，没提到的人只留名字 | 更准 + 更省 token |
| **F5** | JSON 坏了盲重发 | 把坏输出回喂一句"你的输出不是合法 JSON，只输出 JSON"再试 | 比盲重发命中率高（实测有效的手法） |
| **F6** | 没有 max_tokens / 总超时 | `max_tokens≈800`，整体 20 秒超时，超时走纯文本兜底 | 长对话+慢模型会顶到前端 30 秒超时 |
| **F7** | 没有可观测：出了错只能猜 | 每轮记录 `prompt_version / model / 耗时 / token / 工具结果`（存 `chat_messages.actions.meta`，不建新表） | 你反馈"答得不对"时，我能直接看是哪一环 |

## 四、你最关心的：把工具调用显示在对话框里

**现在**：气泡里只有回复 + 一条结果（「☑ 已创建待办：… 去看待办」）。**过程不可见**。

**目标**：每个助手气泡下方一条可折叠时间线：

```
王姐 11-04 生日，要不要我现在给你建个提醒？
─────────────────────────────────
▾ 执行过程                       3 步 · 2.1s
  ├ 识别意图      create_event · create_todo
  ├ 查询人物      王姐 ✓ 匹配 1 人
  ├ 读取上下文    2 条事实 · 1 个事件
  └ 创建待办      11-04 给王姐准备生日礼物 ✓
```

**实现路径（不改表结构）**

| 层 | 改动 |
|---|---|
| 服务 | `execute_actions` 逐步记录 `{step, tool, args_digest, ok, result, ms}`，塞进 `chat_messages.actions`（JSONB 已经是数组，兼容旧数据） |
| 接口 | `TurnOut.actions[]` 增加 `steps` 字段；`GET /messages` 同样返回 |
| 前端 | 气泡下渲染折叠时间线；失败步骤标红；参数只显示摘要（人名/金额/日期），**不显示完整 prompt**（隐私 & 噪音） |
| 测试 | 断言：成功轮有 steps、失败轮 steps 里有 failed 步骤、旧数据（无 steps）不崩 |

工作量估计：后端 2h（含测试）· 前端 2h · e2e 0.5h。

## 五、建议的执行顺序（等你测试反馈后）

| 阶段 | 做什么 | 为什么先做 |
|---|---|---|
| **第 1 批（体验最痛）** | 工具调用时间线（第四节）+ T2 人名模糊匹配 + T3 结构化结果 | 你现在最想看到的；也直接改善"答不对"的体感 |
| **第 2 批（能力缺口）** | T1 `create_ledger` + F2 写操作轻确认 | 口述收付款是真实高频；确认能防"建错了" |
| **第 3 批（稳定性）** | P1 prompt 拆段 + P2 few-shot + F5 结构化修复 | 有第 1 批的时间线做观测，才知道改 prompt 有没有用 |
| **第 4 批（性能）** | F3 流式 + F4 动态上下文 + F6 预算 | 属于打磨，放最后 |
