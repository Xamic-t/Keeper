# Keeper · 项目宪法

> **这是最高层文档。** 与任何其他文档冲突时，以本文为准。
> 修改本文必须写明理由，且不能低于现有严格程度。
>
> 版本：v1.0 · 2026-10-28

---

## 一、业务三原则（不可妥协）

| # | 原则 | 违反的样子 |
|---|---|---|
| 1 | **人只做两件事：投喂和查看** | 任何要求"先整理好再录入"的设计 |
| 2 | **AI 的建议必须带依据** | 只说"建议送茶叶"，不说为什么 |
| 3 | **不确定的交给人，AI 不许硬猜** | 生日、金额、禁忌抽完直接落库 |

**要砍功能时，砍别的，这三条不能砍。**

## 二、工程五纪律

### 纪律 1 · 最小必要封装

> **能用框架的，绝不自己写；要自己写的，必须说清理由且当前就在用。**
> **后端架构要稳，不是要复杂。**

新增任何封装前，依次回答三个问题：

| # | 问题 | 答不上来就别写 |
|---|---|---|
| 1 | 框架有现成机制吗？ | 有 → **必须用** |
| 2 | 这个封装解决什么问题？ | 说不清 → **不写** |
| 3 | 当前代码有调用者吗？ | 只有"以后可能用" → **不写，等用到再加** |

**详细判定标准、准入清单、已删除记录见 [`ARCHITECTURE.md` 19.6 节](./ARCHITECTURE.md#196-最小必要封装原则硬约束)。**

### 纪律 2 · 先改文档，再改代码

| 改什么 | 先改哪 |
|---|---|
| 表结构 | `06-数据库设计` |
| 接口行为 | `07-后端设计` |
| 响应格式 | `10-接口响应规范` |
| 技术选型 / 目录 / 依赖 | `ARCHITECTURE` |

### 纪律 3 · 分层不可越界

`api/` 只接参数调 service · `services/` 不 import fastapi · `models/` 不写查询。
违规判断标准见 `ARCHITECTURE` 11.2。

### 纪律 4 · 数据隔离靠数据库，不靠自觉

多用户隔离由 **PostgreSQL RLS** 强制，不靠应用层写 `where user_id`。
应用连库必须用普通角色 `keeper_app`，**不能用库 owner**（会静默绕过 RLS）。

### 纪律 5 · 隐私红线

日志里**只能出现 `person_id`**，不出现人名和聊天原文。
详见 `ARCHITECTURE` 14.3。

## 三、七类能力必须优先复用框架

| 能力 | 必须用 | 禁止 |
|---|---|---|
| **HTTP 状态码** | 标准码（200/201/204/400/401/403/404/409/413/429/500/502/504） | 自造状态码 |
| **参数校验** | Pydantic `Field` / `Query` / `Path` | 手写 `if not x: raise` |
| **错误处理** | `@app.exception_handler` | 路由内 `try/except` |
| **路由分组** | `APIRouter` + `include_router` | 手动维护路由表 |
| **中间件** | `@app.middleware` / `CORSMiddleware` | 手写 header 处理 |
| **日志** | 标准 `logging` + `extra` | `print()` |
| **依赖注入** | `Depends` | 全局变量 / 自定义装饰器 |

**确需自定义时，必须说明原因，并更新 `ARCHITECTURE`。**

## 四、变更纪律

任何以下变更，**先改 `ARCHITECTURE.md`，再动代码**：

| 变更 | 必须写在 |
|---|---|
| 新增依赖 | 7.6 节（用途 + 替代方案） |
| 调整目录 | 11 节（原因） |
| 自定义错误码 | `core/errors.py` + `07` 的 4.3 节 |
| 更换框架 | 7 节（原因） |

**允许换栈的理由**：安全漏洞无补丁 / 核心依赖停止维护 / 已确认的性能瓶颈。
**不允许的理由**："看起来更先进" / "网上说那个更快" / "想试试新技术"。

---

## 五、违反时怎么办

1. 代码评审时，**指出违反的是哪一条纪律**
2. 能改则改；确实需要例外，**先改宪法并写明理由**
3. **例外不能只存在于代码里**——文档不说，等于没有
