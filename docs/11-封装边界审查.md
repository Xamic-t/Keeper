# 11 · 框架复用与封装边界审查

> **审查对象**：`backend/` 577 行代码（commit `340a62a`）
> **核心问题**：哪些是框架给的？哪些是自己包的？包的这些值不值得？有没有为了显得专业而提前包？
> **方法**：不看注释怎么说，只看**引用次数**和**去掉之后会怎样**。
> 版本：v1.0 · 2026-10-28

---

## 0. 判定标准

| 判定 | 含义 |
|---|---|
| ✅ **必要** | 有实际调用，且去掉会导致重复劳动或格式不一致 |
| ⚠️ **合理预留** | 当前零调用，但**第一个真实业务接口就会用上** |
| ❌ **过度** | 当前零调用，且**V1 结束前可能都用不上**，或与现有实现重复 |

**引用次数统计方法**：`grep -rn` 排除定义行，只数使用点。

## 2. 项目自定义封装（逐一审查）

### 2.1 `core/response.py` — `ok()` / `paginated()`

| 项 | 内容 |
|---|---|
| **解决什么** | 统一响应格式 `{data, meta}`。让"成功响应"只有一种形状 |
| **去掉会怎样** | 每个路由手写 `{"data": ...}`。三个月后一定出现有人写 `{"result": ...}`、有人写 `{"list": ...}` |
| **引用次数** | `ok()` **1 处**（health）· `paginated()` **0 处** |
| **判定** | `ok()` ✅ **必要** · `paginated()` ⚠️ **合理预留** |

**多说一句**：`ok()` 只有 3 行，值得独立文件吗？

值得。**它的价值不是"省几行代码"，是"格式只有一个真源"**。前端改一次，全局生效。

### 2.2 `core/errors.py` — `AppError`

| 项 | 内容 |
|---|---|
| **解决什么** | 业务异常带**业务码 + HTTP 状态码**。框架的 `HTTPException` 只有 `detail`，没有 code |
| **去掉会怎样** | 要么用 `HTTPException`（前端只能读 message 字符串判断分支，改文案就崩），要么每个路由自己 `JSONResponse` |
| **引用次数** | **7 处** |
| **判定** | ✅ **必要** |

**这是整个封装里最必要的一个。** 没有它，"前端按 code 判断"这条规则就无法执行。

### 2.3 `core/errors.py` — `ErrorCode` 枚举（14 个码）

| 项 | 内容 |
|---|---|
| **解决什么** | 错误码集中，避免字符串散落 |
| **去掉会怎样** | `code="NOT_FOUND"` 这种字符串满天飞，改一个漏一个 |
| **引用次数** | **7 处**（但**实际只用上 2 个码**：`UNAUTHENTICATED`、`NOT_FOUND`） |
| **判定** | ⚠️ **轻度提前**——14 个码里 12 个还没被用到 |

**诚实评估**：这是"按设计文档一次性定义"的结果，有点超前。但成本是一个枚举（19 行），收益是**前端能提前看到全表、提前写分支**。可以接受。

### 2.4 `core/errors.py` — 4 个异常处理器

| 处理器 | 解决什么 | 引用次数 | 判定 |
|---|---|---|---|
| `_handle_app_error` | `AppError` → 统一 JSON | 生效中（`get_current_user` 会抛） | ✅ 必要 |
| `_handle_validation` | 把 Pydantic 的冗长错误压成 `{field, reason}` | 生效中（任何参数错） | ✅ 必要 |
| `_handle_http` | 把框架层的 `HTTPException`（405、路由不存在）也转成同一格式 | 未触发过 | ⚠️ **边缘** |
| `_handle_unexpected` | 兜底 500，堆栈只进日志 | 未触发过（没有会崩的路由） | ✅ 必要 |

**`_handle_http` 是可疑项**：业务错误都走 `AppError` 了，`HTTPException` 只剩框架内部抛的几种（405、404 路由）。为这几种写一个 handler 值不值？

**值。** 理由：前端只需要处理**一种**错误格式。否则要判断"这个 404 是框架的 `detail` 还是我们的 `error`"，多一个分支就多一个 bug。

### 2.5 `core/logging.py` — `JsonFormatter` / `setup_logging`

| 项 | 内容 |
|---|---|
| **解决什么** | JSON lines 日志 + 只允许白名单字段进日志 |
| **去掉会怎样** | 用标准文本格式：多行、难 grep、无法接日志系统。且 `extra=` 传什么都会被打出来，**可能把密码打进去** |
| **引用次数** | `JsonFormatter` 1 处 · `setup_logging` 2 处 |
| **判定** | ✅ **必要** |

**`_EXTRA_FIELDS` 白名单不是装饰**：它是一个安全边界——即使某处 `logger.info(..., extra={"password": pwd})`，也不会出现在日志里。这是 ARCHITECTURE 14.3 隐私红线的**执行机制**，不是文档口号。

### 2.6 `deps.py` — 5 个依赖

| 依赖 | 解决什么 | 引用次数 | 判定 |
|---|---|---|---|
| `get_current_user` | 认证（当前是占位，抛 401） | 2 处（被另外两个依赖引用） | ✅ 必要（占位明确） |
| `get_session` | **注入 `SET LOCAL app.user_id`，RLS 的唯一开关** | **0 处** | ⚠️ **合理预留**（W2 第一个业务接口就用） |
| `get_raw_session` | 系统级 session，不带 RLS | **0 处** | ❌ **过度**（见 3.1） |
| `require_owner` | 角色校验 | **0 处** | ⚠️ **边缘**（管理接口可能 V3 才用） |
| `get_pagination` | 分页参数统一 | **0 处** | ⚠️ **合理预留** |

### 2.7 `db.py` — `engine` / `SessionLocal` / `check_database` / `dispose_engine`

| 项 | 解决什么 | 引用次数 | 判定 |
|---|---|---|---|
| `engine` | 连接池、参数集中配置 | 1 处（health 探测） | ✅ 必要 |
| `SessionLocal` | session 工厂 | 2 处（deps.py 两个 session 依赖） | ✅ 必要 |
| `check_database` | 健康探测，只暴露异常类型不泄露连接串 | 2 处 | ✅ 必要 |
| `dispose_engine` | 退出时释放连接池 | 2 处 | ✅ 必要 |

**`SessionLocal` 有 2 处引用，但这 2 处都在 deps.py 里**，而 deps.py 的函数本身零业务调用。所以整条链现在是"悬空"的——这是骨架阶段的正常状态。

### 2.8 `config.py` — `Settings`

| 项 | 内容 |
|---|---|
| **解决什么** | 配置类型化、`SecretStr` 遮蔽、`env_file` 精确定位到项目根 |
| **去掉会怎样** | `os.environ.get("DATABASE_URL", "...")` 散落各处，没有类型、没有默认值、密钥打印时会泄露 |
| **引用次数** | 4 处 |
| **判定** | ✅ **必要**（且是 `pydantic-settings` 的标准用法，不是自造） |

### 2.9 `main.py` — `access_log` 中间件

| 项 | 内容 |
|---|---|
| **解决什么** | 每请求一行 JSON 日志 + `trace_id` + 耗时 + 下发给客户端 |
| **去掉会怎样** | 用 uvicorn 默认 access log：多行、无 trace_id、格式不统一 |
| **引用次数** | 装饰器注册（代码里搜不到名字，属正常） |
| **判定** | ✅ **必要** |

**有一处可疑**：中间件里用 `try/except` 包了 `call_next`。但 Starlette 的 `ExceptionMiddleware` 在更外层，异常通常不会冒到这里。

**结论**：这段是防御性的，可能永远不触发。**不算过度**（10 行），但属于"想多了"。

## 3. 判定为"过度"的部分

### 3.1 `get_raw_session` —— 唯一真正多余的一个

```python
async def get_raw_session() -> AsyncGenerator[AsyncSession]:
    """系统级 session，不带 RLS。
    只允许三处使用：登录、健康检查、定时任务。
    """
```

| 问题 | 说明 |
|---|---|
| **引用次数** | **0** |
| **更严重的是自相矛盾** | 注释说"健康检查用它"，但 `api/health.py` 实际用的是 `engine.connect()`（更底层的直连探测），**根本没走它** |
| **后果** | 一段声称有明确用途、但实际没有任何调用者的代码。三个月后看到会困惑："这个到底该不该用？" |

**处理建议（二选一）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 删掉** | 等 W2 写登录时再加（5 行） | 现在删，W2 加回来 |
| **B. 改注释** | 说明"健康检查用更底层的 engine 探测，不经过 session" | 保留一段零调用代码 |

**我倾向 A**。理由：零调用的封装会腐烂——没人用的代码，没人验证它是对的。

### 3.2 14 个错误码里的 12 个（轻度）

只用了 `UNAUTHENTICATED` 和 `NOT_FOUND` 两个。剩下的 12 个是"提前定义"。

**但这条我不建议改**。因为错误码表本来就是**接口契约的一部分**，前端要提前看到全表才能写分支。枚举的成本（19 行）远低于它的价值。

## 4. 汇总判定

| 分类 | 数量 | 占比 |
|---|---|---|
| ✅ 必要封装 | 11 | 61% |
| ⚠️ 合理预留（第一个业务接口就会用） | 5 | 28% |
| ❌ 过度（零调用且用途矛盾） | 1 | 6% |
| ⚠️ 边缘（可能 V3 才用） | 1 | 6% |

**结论**：

> **没有为了"显得专业"而过度封装。** 唯一真正多余的是 `get_raw_session`（零调用 + 注释与实际不符）。
>
> 5 个"合理预留"加起来约 40 行，占全部代码的 7%。它们的判断依据是**"W2 第一个业务接口就会调用"**——不是"以后可能有用"。

## 5. 一个更值得警惕的现象：悬空链路

比"提前封装"更值得注意的，是**整条链路现在是悬空的**：

```
api/health.py ──→ db.check_database() ──→ engine.connect()
                                            ↑
                                    这条是通的（已验证）

未来的业务路由 ──→ deps.get_session ──→ SessionLocal ──→ engine
                    ↑
              这条整条零调用，从未被验证过
```

`get_session` 里的那行 `SET LOCAL app.user_id`，**是整个多用户隔离的开关**，但它现在**一次都没有真实执行过**。

这不是封装的问题，是**骨架阶段的必然**。但要清楚：

> **"RLS 设计好了"和"RLS 验证过"是两件事。** 前者是文档，后者要等 W1 建表 + W2 第一个业务接口才能证明。

---

## 6. 建议

| # | 建议 | 理由 |
|---|---|---|
| **1** | **删掉 `get_raw_session`** | 零调用 + 注释与实际不符，是唯一真正多余的 |
| **2** | 保留 `get_pagination` / `paginated` / `get_session` | 第一个业务接口必用，40 行换"不用改架构" |
| **3** | 保留 `require_owner`，但标注"当前零调用" | 8 行，且是三层权限的设计要求 |
| **4** | `access_log` 的 `try/except` 可以删 | 异常到不了这一层，是防御性冗余 |
| **5** | 14 个错误码保持不动 | 是接口契约，不是过度设计 |
| **6** | **W2 第一个业务接口跑通后，回来复查本文** | 那时"合理预留"会变成"已验证"，悬空链路会被打通 |

---

## 7. 一句话总结

> **这套封装里，最必要的三个是 `AppError`、`JsonFormatter` 的字段白名单、`get_session` 的 SET LOCAL——它们各自守住了一条不能靠自觉的边界（错误码稳定、隐私不泄露、数据不串）。**
>
> **最不必要的一个是 `get_raw_session`——它证明了一件事：零调用的封装会腐烂。**
