## 1. 产品骨架：三层时间

关系维护本质上是**时间管理**。所有功能都挂在三个时间维度上，这个框架决定了信息架构：

```
┌─────────────────────────────────────────────────┐
│  过去  │  发生过什么                             │
│        │  时间线 · 往来账 · 历史事件 · 原始截图     │
├─────────────────────────────────────────────────┤
│  现在  │  这个人现在什么状态                      │
│        │  双层画像 · 关系温度 · 活跃窗口            │
├─────────────────────────────────────────────────┤
│  未来  │  什么时候该做什么                        │
│        │  日历 · 提醒 · 待办 · 需求感知            │
└─────────────────────────────────────────────────┘
```

**"现在"这一层是产品的灵魂**，也是传统工具缺失的一层。CRM 有过去（记录）和未来（任务），但没有"这个人现在跟我是什么状态"。

## 2. 功能清单

标注说明：**V1** = 第一版必须有（记忆系统）；**V2** = 第二版（判断系统）；**V3** = 泛化期。

### 模块一 · 投喂（Input）

| # | 功能 | 版本 | 说明 |
|---|---|---|---|
| 1.1 | **截图投喂** | V1 | 支持一次多张、手机相册直选、微信分享直达。AI 判断"是不是聊天记录"→ 识别双方 → 归属 |
| 1.2 | **文字快记** | V1 | 一句话（"陈姐家猫生病了"）→ 意图识别 → 归属 → 抽成事实 |
| 1.3 | **手动补录** | V1 | 表单兜底，不经过 AI。生日、金额这类硬信息允许直接填 |
| 1.4 | **确认队列** | V1 | 抽取结果以卡片流呈现，逐条 ✓/✗/改。**这是产品质量的闸门** |
| 1.5 | **语音投喂** | V2 | 说一句话转文字，复用 1.2。走路时也能喂 |
| 1.6 | **批量归档** | V2 | 一次导入历史截图（如首次使用时导入三个月聊天） |

**投喂是唯一入口，它的体验决定产品生死。** 目标：从"想记一件事"到"记完"，不超过 15 秒。

### 模块二 · 人（Person）

| # | 功能 | 版本 | 说明 |
|---|---|---|---|
| 2.1 | **档案主页** | V1 | 打开一个人，第一眼是 AI 综述，下面依次是标签、时间线、往来账、待办 |
| 2.2 | **AI 综述** | V1 | 约 150 字的人物画像，**每次有新事实就自动重写** |
| 2.3 | **标签体系** | V1 | 五类标签（见 2.3.1），可筛选、可统计 |
| 2.4 | **时间线** | V1 | 事实 + 往来 + 事件按时间混排，一条线看完所有交互 |
| 2.5 | **多重关系视角** | V1 | 一个人可同时是"哥姐"和"客户"，两个角色各自的阶段、价值、话术 |
| 2.6 | **关系温度** | V2 | 0-100 分 + 趋势 + 依据，驱动活跃窗口和提醒优先级 |
| 2.7 | **记忆过期提示** | V2 | 半衰期到期的事实自动降权，提示"这条还准吗" |

#### 2.3.1 标签体系（五类）

| 类别 | 举例 | 来源 | 是否可筛选 |
|---|---|---|---|
| **事实型** | 行业=建材、家庭=有一女高二、地域=杭州 | AI 抽取 | 是 |
| **偏好型** | 喜欢茶、讨厌甜食、爱拍照 | AI 抽取 | 是 |
| **场景型** | 装修中、孩子高考、最近生病 | AI 抽取（**带半衰期**） | 是（默认只显示未过期的） |
| **价值型** | 消费档=高、打赏等级=铁粉、累计 1.2 万 | 计算得来 | 是 |
| **关系型** | 关系阶段=核心、温度=78↑、认识 2 年 | 计算得来 | 是 |

> **关键设计**：`场景型`标签必须带过期时间。这是"动态画像"和"静态标签"的分水岭。详见 `03-数据与技术.md` 第 3 节。

### 模块三 · 事（Event & Ledger）

| # | 功能 | 版本 | 说明 |
|---|---|---|---|
| 3.1 | **往来账** | V1 | 一张表：方向（他给我/我给他）× 类型（打赏/订单/礼物/收付款）× 金额 × 日期 × 结款日 |
| 3.2 | **日历** | V1 | 五类事件：生日、节日节气、结款到期、待办截止、自定义。支持农历 |
| 3.3 | **消费价值合并计算** | V1 | 一个人的总价值 = 打赏 + 订单 + 转介绍，不按关系类型分开算 |

**为什么往来账必须和关系绑在一起**：因为你维护的不是"一笔笔交易"，是"一个人"。打开王姐的档案，要能一眼看到她给你打赏多少、从你这买过多少、你送过什么——**这才是"关系"的完整账本**。

### 模块四 · 行动（Action）

| # | 功能 | 版本 | 说明 |
|---|---|---|---|
| 4.1 | **今日页** | V1 | 打开系统默认页：今天该做的 3 件事 + 待确认卡片数 + 新动态 |
| 4.2 | **提醒** | V1 | 日期驱动（生日 7/3/0 天、结款 3/0 天、节日）+ **AI 建议（带依据）** |
| 4.3 | **待办** | V1 | 固定模板（下播 SOP）+ AI 动态生成（走确认队列） |
| 4.4 | **提醒转待办** | V1 | 提醒一键变任务，闭环 |
| 4.5 | **状态驱动提醒** | V2 | 温度变化触发："李哥两周没动静，降了 12 分，要不去说句话？" |

#### 4.2.1 提醒卡片长什么样（V1 的核心交付物）

这是产品的"脸"，必须设计到能直接截图给评委看：

```
┌────────────────────────────────────────────┐
│  [生日 · 还有 3 天]  王姐 · 建材 · 核心       │
│                                            │
│  🎁 建议下单：白茶礼盒  ￥300-500            │
│                                            │
│  依据：                                     │
│  · 她 10-03 说过"最近在喝白茶"              │
│  · 去年送的是香水，不重复                    │
│  · 档案禁忌：不提年龄                       │
│                                            │
│  💬 话术（点一下复制）：                     │
│  "姐，这几天降温记得添衣。上次你说爱喝白茶，   │
│   我托人带了点，不贵重，你尝尝。"             │
│                                            │
│  [ 转待办 ]  [ 换一个建议 ]  [ 今年不送 ]     │
└────────────────────────────────────────────┘
```

**三条硬规则**（对应原则二、三）：

1. 每条建议**必须**带依据，格式为"因为 [来源]，所以建议 [结论]"
2. 若档案有禁忌，建议必须显式规避
3. 若往年送过同类，必须提示并给替代方案
4. **不输出精确金额对比**（"她刷了 8000，你回 800"这种话会毁掉关系）

### 模块五 · 判断（Intelligence）— V2 主体

| # | 功能 | 版本 | 说明 |
|---|---|---|---|
| 5.1 | **关系温度** | V2 | 五维打分 → 0-100 + 趋势；驱动活跃窗口 |
| 5.2 | **需求感知** | V2 | 温度 × 场景 的 2×2 判断（见 `01` 第 6.2 节） |
| 5.3 | **对话式问答** | V2 | 混合检索路由：精确事实/跨人筛选走 SQL，模糊回忆走 RAG |
| 5.4 | **活跃窗口管理** | V2 | 进窗口/出窗口规则，推送总量控制 |

**V1 不做温度，但不能不做架构**：数据模型必须预留温度计算所需的全部字段（互动时间、频次、金额趋势），否则 V2 要返工。

|---|---|---|---|

## 3. 核心场景

五个真实场景，产品设计必须服务它们。

### 场景一：下播后批量归档（最高频）

> 晚上 11 点，下播。今天有 8 个人私信过。手机相册里躺着 12 张截图。

**现在**：一张张翻，看完了不知道记什么，全靠脑子。

**用系统**：相册多选 12 张 → 上传 → 去洗澡 → 回来看到 9 张确认卡片，已经按人分好组 → 逐条点 ✓，两条改归属，一条 ✗（"这句是开玩笑的，不用记"）→ 完事，3 分钟。

**设计要求**：手机端必须能直接调相册多选；上传后可离开，后台处理；结果按人分组，不按时间排。

### 场景二：生日前 3 天（最有价值）

> 早上 8 点，企业微信弹一条。

**现在**：靠脑子记，或者日历提醒"王姐生日"——然后你还要自己想送什么、说什么。

**用系统**：提醒卡片直接给方案 + 依据 + 话术。点"转待办"，下班路上就把单下了。

**设计要求**：建议必须具体到可执行（送什么、多少钱、说什么），而不是"记得给王姐发生日祝福"。

### 场景三：见面前临时抱佛脚（次高频）

> 下午要见张总，路上 10 分钟。

**现在**：翻微信聊天记录，翻到一半到地方了。

**用系统**：打开档案，先读 150 字综述：**"张总，45 岁，做建材批发，两个门店，太太管账。喜欢喝浓茶、抽烟但戒了三次。去年底提过想扩店但缺资金。忌讳聊他儿子（复读两年）。上次沟通 10-12。"**

10 秒读完，知道该怎么聊、别踩什么雷。

**设计要求**：综述必须是"能直接用于对话的信息"，不是标签堆砌。

### 场景四：随手记一句（最低成本）

> 中午刷朋友圈，看到陈姐发了猫在输液的照片。

**现在**：心里记一下，晚上就忘了。

**用系统**：截图朋友圈 → 上传 → 一张卡片："要给陈姐记一条：家里猫生病了 → ✓"。3 秒。

**设计要求**：单张投喂要极快，甚至支持微信分享直达（不用打开 App）。

### 场景五：判断这个人是不是凉了（V2）

> 突然想起李哥，好像很久没来了。

**现在**：翻记录，发现上个月还在，说不清是忙还是凉了。

**用系统**：温度 42↓（-18），依据："上次互动 26 天前 / 近 30 天消息量下降 70% / 上月打赏中断"。**提示："他可能只是忙，也可能真的在疏远。建议轻量问候，不要提打赏。"**

**设计要求**：温度必须可解释、措辞必须留余地，不能说"他不要你了"。

## 4. 主流程

### 4.1 投喂流程（核心链路）

```
① 手机上选图 / 粘贴文字
        ↓
② 上传到服务器，立即返回"已收到"（异步处理）
        ↓
③ AI 第一跳：这是不是聊天记录？
        ├─ 不是 → 走文字抽取路径
        └─ 是 → 提取发言人与内容、时间戳
        ↓
④ AI 第二跳：这是和谁的？
        ├─ 高置信 → 直接归属
        └─ 低置信/多人 → 标记"待确认归属"
        ↓
⑤ AI 第三跳：三路抽取
        ├─ 事实（喜好/家庭/工作/动态/禁忌）
        ├─ 事件（生日/约定/结款日）
        └─ 往来（打赏/订单/礼物/收付款）
        ↓
⑥ 生成确认卡片，按人分组，置信度排序
        ↓
⑦ 用户逐条处理：✓ / ✗ / 改归属 / 修改内容
        ↓
⑧ 落库 + 级联更新
        ├─ 画像综述重写
        ├─ 价值档重算
        ├─ 事件写入日历
        └─ 抽取日志归档（含用户处置）
```

**关键设计**：第 ⑦ 步不是"审核"，是**产品的核心体验**——用户在这里第一次感到"AI 真的看懂了"。所以卡片必须显示**原文出处**，让人一眼判断对错，而不是让他去回忆。

### 4.2 提醒流程

```
每日 08:00 定时任务
        ↓
扫描未来 7 天的所有事件
        ↓
命中提醒档位？
        ├─ 生日：7 天 / 3 天 / 当天
        ├─ 结款：3 天 / 当天
        └─ 节日：提前 2 天
        ↓
为每条命中生成提醒内容：
        ① 拉该人完整档案（硬字段 + 标签 + 综述）
        ② 检索记忆层（关于这件事他说过什么）
        ③ 检索知识层（这类人/这个预算送什么）
        ④ 查历史往来（往年送过什么，防重复）
        ↓
生成三部分：事实陈述 + 行动建议（2-3 个选项）+ 话术
        ↓
通道推送：企业微信 → 失败降级 PushPlus
        ↓
用户点开 → 转待办 / 换建议 / 忽略
```

### 4.3 查询流程

**V1：结构化的"看"**

```
今日页 → 点某人 → 档案页（综述 → 标签 → 时间线 → 往来账）
人物列表 → 筛选（按标签/温度/阶段）→ 进入档案
```

**V2：对话式的"问"**

```
用户提问 → 意图分类
    ├─ 精确事实（王姐生日几号）→ SQL → 直接答
    ├─ 跨人筛选（谁喜欢茶）→ SQL + 标签 → 列表
    ├─ 模糊回忆（她上次说的那事）→ 向量检索（按人分区）→ 带出处的回答
    └─ 知识增强（送什么）→ 知识库 + 档案 → 建议 + 依据
```

## 5. 用户路径

### 5.1 Day 0：第一次打开（决定留存的 5 分钟）

```
打开网页 / 添加到主屏
  ↓
空状态：不要给我看空表格
  ↓
引导：「先随便丢一张聊天截图试试」
  ↓
上传 → 30 秒后 → 出现第一张确认卡片
  ↓
点 ✓ → 出现第一个人的档案，里面已经有 3 条事实 + 一段综述
  ↓
"这就是它替你记住的"
```

**第一天必须让用户看见"AI 真的读懂了一张图"。** 这一下比任何功能介绍都有效。

### 5.2 第一周：建立习惯

| 时间 | 行为 | 系统要做的 |
|---|---|---|
| Day 1-3 | 每天投喂 3-5 张 | 确认准确率要高（宁可少抽，不可错抽） |
| Day 4-7 | 开始随手记文字 | 归属判定要准（猜错一次就烦） |
| 第 7 天 | —— | **必须出现第一条有价值的提醒**（哪怕是"某某 20 天没联系了"） |

> **第一周没有提醒 = 用户流失。** 所以 V1 必须在 Day 7 前至少有一条日期事件命中；如果用户档案里没有生日，系统应主动引导补录。

### 5.3 第一个月：形成信任

- 收到 2-5 条生日/结款提醒，**按建议执行了，结果不错**
- 打开档案查人的次数超过 5 次
- 开始主动补录（说明他认可了这个账本）

### 5.4 长期：从工具到习惯

一年后理想状态：**全年不用记任何人的生日，不用想送礼送什么，不用翻聊天记录找话说。**

## 6. 关键界面设计

### 6.1 今日页（默认首页）

信息层级，从上到下：

```
① 今天该做的（最多 3 条，超出折叠）
   —— 生日提醒 / 结款到期 / 待办
② 待确认（N 张卡片）           ← 红点，最强视觉权重
③ 最近动态（谁更新了档案、谁有新事实）
④ 一句话快记入口（悬浮，常驻）
```

**为什么"待确认"排第二但视觉最强**：因为它是用户唯一的"工作"，其余都是阅读。

**为什么"今天该做的"最多 3 条**：20 人规模下，超过 3 条说明系统在制造焦虑，不是在帮忙。

### 6.2 投喂页

**一个巨大的上传区，没有别的。**

- 手机：调相册（多选）/ 拍照 / 粘贴板
- 电脑：拖拽 / 粘贴（Ctrl+V 直接贴图）
- 上传后立刻返回，处理在后台，完成后推送通知

**不要在这里放任何设置项。** 投喂是一个"动作"，不是一个"页面"。

### 6.3 确认队列

**卡片流，按人分组，不按时间。**

```
【王姐】3 条待确认
  ┌─────────────────────────────────┐
  │ 事实 · 偏好            置信 0.92 │
  │ "最近在喝白茶"                    │
  │ 出处：10-03 聊天 第 3 屏 [查看原图]│
  │ [✓] [✗] [改]                    │
  └─────────────────────────────────┘
  ┌─────────────────────────────────┐
  │ 往来 · 打赏 in          置信 0.88 │
  │ ￥520 · 10-05                    │
  │ 出处：转账截图 [查看原图]          │
  │ [✓] [✗] [改]                    │
  └─────────────────────────────────┘
```

三条交互规则：

1. **出处永远可见**，点开看原图 —— 这是"敢不敢信"的关键
2. **低置信度（< 0.7）标黄**，但仍默认勾选 ✓（少点一次）
3. **改归属**：卡片顶部显示当前归属人，点一下换成别人（从最近 20 人里选，带搜索）

### 6.4 人物档案页

```
┌──────────────────────────────────────┐
│ 王姐                        [编辑]     │
│ 建材 · 核心 · 认识 2 年 · 温度 78↑     │
├──────────────────────────────────────┤
│ 📝 AI 综述（自动更新，可手动改）        │
│ 王姐，38 岁，做建材生意，有个上高二的    │
│ 女儿。喜欢喝白茶、讨厌太甜的东西。最近   │
│ 在装修，忌讳聊年龄。上次沟通：10-03。    │
├──────────────────────────────────────┤
│ 🏷 标签                                │
│ 行业:建材  家庭:一女高二  偏好:白茶/淡口 │
│ 场景:装修中(剩 2 月)  价值:高  关系:核心 │
├──────────────────────────────────────┤
│ 📅 时间线                              │
│ 10-05  打赏 ￥520                     │
│ 10-03  "最近在喝白茶"                  │
│ 09-28  订单 ￥1800（已结）             │
├──────────────────────────────────────┤
│ 💰 往来汇总                            │
│ 他给我 ￥12,400 ｜ 我给他 ￥3,200       │
└──────────────────────────────────────┘
```

**信息顺序不能变**：综述 → 标签 → 时间线 → 往来。因为用户打开档案的目的是"我要跟他说话"，先给"感觉"，再给"检索"，最后给"账"。

### 6.5 提醒消息（企业微信内）

见 4.2.1。要点：**在聊天软件里就能读完并行动**，不需要跳回系统。

## 7. 交互细节约定

| 场景 | 规则 |
|---|---|
| AI 归属猜错 | 卡片上一键改，改完记录到日志（用于优化），**不弹二次确认** |
| 抽取置信度低 | 标黄但仍默认 ✓，允许直接批量确认 |
| 重复投喂同一张图 | 按图片 hash 去重，提示"这张已经传过了" |
| 抽取为空 | 明确告知"这张没抽出有用信息"，而不是假装成功 |
| 用户改了 AI 结果 | 记录 diff（原文 vs 用户改后），这是最有价值的训练数据 |
| 删除一个人 | 二次确认 + 说明会删掉什么（档案/截图/往来/日志） |
| 原图保留 | 默认保留，提供"仅存文字"开关（省空间） |
