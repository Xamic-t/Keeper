## 一、产品形态：响应式 Web + PWA

**唯一形态，不做小程序、不做 App、不做纯后端。**

| 维度 | 结论 |
|---|---|
| 载体 | 浏览器（手机 + 电脑同一个网址） |
| 安装感 | PWA：添加到主屏后有图标、全屏打开、无地址栏 |
| 投喂方式 | 手机相册多选上传（iOS/Android 原生支持 `<input type="file" multiple>`） |
| 推送 | 不走 Web Push，**走企业微信群机器人 webhook** |
| 离线 | Service Worker 缓存壳，弱网可打开（不做离线写入） |

### 1.1 为什么不是别的（这三条写进论文的"方案对比"）

| 方案 | 为什么不做 |
|---|---|
| **微信小程序** | 投喂体验确实最好（微信内可直接分享图），但三处硬伤：① 个人主体功能受限，AI 类目审核易卡；② **订阅消息是一次性授权**，长期主动提醒做不了——这和"主动提醒"的核心直接冲突；③ 另写一套 WXML，前端一般的成本翻倍 |
| **原生 App** | 一个人几个月做不起：iOS/Android 两套、上架审核、签名证书、发版更新。且需求里**没有任何一条是 App 才能做的** |
| **纯后端 + IM Bot** | 界面能力为零，做不了档案页、日历、卡片流。可作为**二期补充入口**（企业微信自建应用收图），但不作为主形态 |
| **Streamlit / Gradio** | 写起来最快，但移动端体验差、样式不可控、做不了卡片流逐条确认——直接违背"手机优先" |

### 1.2 PWA 的两个必做项

1. `manifest.json`：名称、图标（192/512）、`display: standalone`、主题色
2. `sw.js`：只缓存静态壳（JS/CSS/图标），**不缓存业务接口**（数据要新）

> ⚠️ PWA 必须 HTTPS。所以域名备案是国内部署的**前置条件**，不是可选项。

## 二、前端：Vue 3（为什么不选 React）

**结论：Vue 3 + TypeScript + Vite + Tailwind CSS + Pinia + Vue Router。**

### 2.1 Vue 与 React 对这个项目的实际差异

| 维度 | Vue 3 | React 18/19 |
|---|---|---|
| **模板语法** | 接近 HTML，和你看过的 Jinja2 一个路子 | JSX，要在 JS 里写标签，还要记 `className`、`{}` 插值 |
| **响应式** | 自动追踪依赖，改数据视图就更新 | 手动管依赖数组，`useEffect` 漏依赖是新手第一大坑 |
| **心智负担** | 一个 `.vue` 文件 = 结构 + 逻辑 + 样式 | 组件、hooks、闭包、重渲染，概念多一层 |
| **中文资料** | 官方中文文档质量极高，社区教程多 | 英文为主，中文多为二手 |
| **上手速度** | 一天能写出能用的页面 | 一周能写出能用的页面 |
| **组件库** | Element Plus / Naive UI（中文文档好） | shadcn/ui（需自己拼 Tailwind） |
| **AI 生成质量** | 好 | **更好**（训练数据更多） |
| **生态规模** | 大 | 最大 |

**决定性理由**：你的痛点是"前端一般"，不是"需要极致性能"。Vue 的模板语法和自动响应式，恰好把后端开发者最容易踩的两个坑（JSX 心智负担、依赖数组）直接消掉了。

**唯一的劣势**是 AI 生成 Vue 代码的质量略低于 React。三个对冲手段：

1. 只用 `<script setup lang="ts">` 这一种写法（最主流，训练数据最多）
2. 不用冷门语法（不写 `defineExpose` 花样、不写 render 函数）
3. 组件库只用最主流的（如果加装）

### 2.2 完整前端清单

| 项 | 选型 | 说明 |
|---|---|---|
| 框架 | **Vue 3** | `<script setup>` + Composition API |
| 语言 | **TypeScript** | 理由见 2.3 |
| 构建 | **Vite 5+** | 一条命令起项目，热更新快 |
| 路由 | **Vue Router 4** | 官方，五个页面够用 |
| 状态 | **Pinia** | 官方推荐，比 Vuex 简单得多 |
| 样式 | **Tailwind CSS** | 响应式断点好控，手机优先 |
| 日历 | **@fullcalendar/vue3** | MIT 核心版，`eventContent` 返回 Vue 组件 |
| HTTP | **fetch 封装**（不用 axios） | 需求简单，少一个依赖 |
| 图标 | **Lucide Vue** | 按需引入 |
| 类型生成 | **openapi-typescript** | 从后端 OpenAPI 自动生成前端类型 |

### 2.3 为什么用 TypeScript

不是为了"高级"，是为了**少一类 bug**：

- 后端 Pydantic 模型 → OpenAPI → 自动生成前端 TS 类型
- 后端字段改名，前端立刻红字报错，而不是运行时才发现 `undefined`
- 前端的 `Person`、`Fact`、`Ledger` 类型和后端永远一致

**这一条能省掉前后端联调中最多的那类问题。** 而且它是自动生成的，你不需要手写。

### 2.4 组件库：先不用，需要时再加

**结论：V1 不引入 Element Plus 这类重型 UI 库。**

理由：

1. 这个项目**手机优先**，而 Element Plus / Ant Design 都是桌面后台思维，移动端样式要大量覆盖
2. 你真正需要的组件都很基础：卡片、列表、按钮、输入框、上传、弹窗、Toast——**Tailwind 写出来比改组件库快**
3. 重型库会把包撑到几百 KB，PWA 首屏变慢

**唯一的例外**：日历用 FullCalendar（自己写不出来）。

> 如果写到一半觉得手写组件太慢，可以**按需引入 Element Plus 的单个组件**（如 `ElMessage`、`ElDialog`），不要整包引入。

### 2.5 实现顺序：先功能，后样式

前端分两阶段做，不要一开始就追求好看：

| 阶段 | 时间 | 目标 | 不做什么 |
|---|---|---|---|
| **一 · 能用的丑版** | W4-W10 | 流程能跑通，你自己能真的用它 | 不引入设计系统、不写动画、不做响应式精修 |
| **二 · 换皮** | W11-W12 | 按 `docs/design/` 的 v5 重做样式层 | 不动路由、不动 API、不动状态 |

**为什么换皮不会返工**：因为设计 token（颜色、字号、间距、圆角）是独立的一层，换皮 = 改 `tailwind.config.js` + 重写组件的模板部分，数据流一行不动。

**唯一的前提**：阶段一就必须把 `api/client.ts`、`router`、`stores` 写对。这三个是骨头，样式是皮。**皮可以换，骨头不能歪。**

### 3.2 后端框架：FastAPI 到底给了你什么

#### 3.2.1 先认清它的类型

**FastAPI 是微框架，不是 Django 那种全家桶。**

它只解决一段：`HTTP 请求进来 → 校验参数 → 调你的函数 → 返回 JSON`。其余全部要自己选。

如果抱着"装上就有后台管理、用户系统、ORM"的期待来，会失望。**但正因为不管这些，你才有得选。**

| | Django | Flask | **FastAPI** |
|---|---|---|---|
| 类型 | 全家桶 | 微框架 | 微框架 + 现代 |
| ORM | 自带 | 无 | 无 |
| 后台管理 | 自带 admin | 无 | 无 |
| 用户/权限 | 自带 | 无 | 无 |
| 自动 API 文档 | 需插件 | 需插件 | **自带** |
| 类型校验 | 无 | 无 | **Pydantic 内置** |
| 异步 | 3.1+ 支持 | 需 ASGI | **原生** |
| 学习曲线 | 陡（要学一堆约定） | 平 | 中 |

#### 3.2.2 为什么这个项目选它

1. **Pydantic 正好校验抽取结果**——VLM 返回的 JSON 字段缺失、类型错、多抽少抽都常见，schema 写一次校验就有了
2. **自动 OpenAPI 是前端类型的源头**——`openapi-typescript` 从 `/openapi.json` 生成 TS 类型，前后端字段永远对得上
3. **异步原生**——调模型要等几秒，异步不阻塞其他请求
4. **依赖注入天然适配 RLS**——每个请求注入一个带 `SET LOCAL app.user_id` 的 session，隔离不靠自觉
5. **AI 熟悉度最高**——训练数据多，生成代码质量高，遇到问题搜得到答案

第 5 条是实打实的工程收益：**你前端一般、项目一个人做，出问题时能不能搜到答案，比框架先不先进重要得多。**

#### 3.2.3 框架自带的（不用装）

| 能力 | 用什么 |
|---|---|
| 路由分组 | `APIRouter` |
| 请求/响应校验 | Pydantic v2 |
| 依赖注入 | `Depends` |
| **API 文档** | `/docs`、`/redoc`、`/openapi.json` 自动生成 |
| 异步 | `async def` |
| 后台任务 | `BackgroundTasks`（够用，不需要 Celery） |
| CORS | `CORSMiddleware` |
| 生命周期 | `lifespan`（连库、起定时任务） |
| 测试客户端 | `TestClient`（基于 httpx） |
| WebSocket | 内置（本项目不用） |
| 文件上传 | 需 `python-multipart`（唯一必装的小依赖） |

| 能力 | 选什么 | 为什么不自带 |

| **ORM** | SQLModel | FastAPI 刻意不绑定 ORM |

#### 3.2.5 官方目录规范：其实没有

FastAPI 官方**不强制目录结构**，只在 "Bigger Applications" 教程里给了一个多文件示例：

```
app/
├── __init__.py
├── main.py
├── dependencies.py
└── routers/
    ├── __init__.py
    ├── users.py
    └── items.py
```

就这些。**没有 models / services / repositories 的分层规定。**

这是它和 Django 最大的文化差异：**Django 有 opinion，FastAPI 没有。** 好处是自由，坏处是不定规矩就会长成一锅粥——所以规矩得我们自己定。

**三条分层纪律（比目录本身重要）**：

1. **`api/` 不写业务逻辑**——只做参数解析、调 service、返回模型。函数超过 30 行就说明逻辑放错地方了
2. **`services/` 不 import fastapi**（`HTTPException` 除外）——这样每个 service 都能用 pytest 单独跑，不用起 HTTP
3. **`models/` 只定义表，不写查询**——查询放 service 里，因为查询往往要带权限和业务条件

#### 3.2.7 什么时候不该选 FastAPI

诚实地说三条，我们都不沾，但你要知道边界：

| 情况 | 该选什么 |
|---|---|
| 需要一个开箱即用的后台管理界面 | **Django**——admin 能省一个月 |
| 要做服务端渲染的整站（有 SEO 要求） | Django / Flask |
| 团队只会 Django | 别为了先进性换栈 |

本项目是 API + 独立前端（Vue SPA），不需要 admin、不需要 SSR、只有你一个人用 FastAPI，所以上面三条都不适用。

## 四、关键技术判断

### 4.1 前后端分离的三个坑，以及怎么填

选了 Vue 就必须面对这三个问题，提前说清楚：

| 坑 | 表现 | 解法 |
|---|---|---|
| **CORS** | 开发时前端 5173 调后端 8000 被浏览器拦 | 开发用 Vite `proxy` 转发 `/api`；**生产同域部署**（Caddy 一个域名同时托管前端和反代 API），根本不产生跨域 |
| **类型不同步** | 后端改了字段名，前端还在用旧的 | `openapi-typescript` 从 `/openapi.json` 生成类型，改一次跑一次 |
| **部署两套** | 前端要 build，后端要重启 | 一个 `deploy.sh` 里两步串起来；前端产物由 Caddy 直接托管，不单独起 Nginx |

**同域部署是关键**——它一次性消掉了 CORS、cookie 跨域、证书三个问题。

```
https://yourdomain.com/          → Caddy 返回 frontend/dist 里的静态文件
https://yourdomain.com/api/*     → Caddy 反代到 FastAPI:8000
```

### 4.2 账号与鉴权

#### 4.2.1 账号：统一登录名，不上短信

**结论：只有一个 `username` 字段，允许填用户名 / 手机号 / 邮箱，不校验格式、不验证真实性。**

先说清一个常见误解：**手机号登录并不需要短信验证码。** 短信只解决一件事——证明"这个号是你的"；它不解决"能不能登录"，登录靠的是密码。

| 方案 | 成本 | 代价 |
|---|---|---|
| **用户名 + 密码** | 零 | 无 |
| **手机号 + 密码（不发短信）** | 零 | 号填错也没人知道；找回密码只能找管理员 |
| **手机号 + 短信验证码** | 约 0.04 元/条 | **流程成本高**：开通云短信、实名、签名审核 1-2 天、模板审核，且签名要求域名已备案 |

**为什么不上短信**：钱不是问题，流程是问题。20 人以内、邀请制、账号由你手动创建，天然可信——这一层验证没有收益，只有一周的等待。

**统一登录名的好处**：用户想填哪种就填哪种，三种方式同时成立，而系统只当成一串唯一标识。

**什么时候才需要真的上短信**：

1. 开放注册（要防垃圾账号）
2. 用户量超 50，管理员手动重置密码成了负担
3. 手机号要作为真实身份（比如接入短信通知）

**升级路径**：加 `phone` + `phone_verified_at` 两列，登录逻辑一行不改。

#### 4.2.2 注册与找回（V1 最简）

| 环节 | V1 做法 | 以后再说 |
|---|---|---|
| 注册 | **管理员后台建号**，设初始密码，线下告诉用户 | 邀请码 + 自助注册 |
| 找回 | **管理员重置** | 邮件重置（需 SMTP）/ 短信重置 |

> 20 人以内，管理员重置密码完全扛得住。不要为了一个可能用不到的功能去接 SMTP 或短信。

#### 4.2.3 密码与会话

- 密码：**argon2id** 哈希，不存明文，不可逆
- 登录失败：连续 **5 次锁 15 分钟**，成功登录清零
- 会话：**httpOnly cookie + SameSite=Lax**，同域部署
- CSRF：`itsdangerous` 签短串，放请求头

#### 4.2.4 为什么不用 JWT

| 方案 | 优点 | 缺点 |
|---|---|---|
| JWT（存 localStorage） | 前后端彻底解耦，移动端通用 | XSS 能偷 token；要处理过期刷新；登出要黑名单 |
| **httpOnly cookie** | XSS 偷不到；登出就是删 cookie | 需要同域（已满足） |

**结论**：同域 + 单用户，cookie 更简单也更安全。JWT 的那点好处在这里用不上。

### 4.3 数据库：PostgreSQL，以及它顺带解决的三个问题

选 Postgres 的直接理由是"后面要多用户"。但它同时补上了三个你现在没提、却同样关键的能力：

| 能力 | 具体是什么 | 为什么这个项目需要 |
|---|---|---|
| **RLS 行级安全** | 数据库层强制 `user_id = current_setting('app.user_id')::int` | 多用户隔离不靠应用代码自觉——写漏一个 `where user_id` 也不会串数据 |
| **JSONB + GIN 索引** | `roles`、`taboo`、`platform_ids`、`role_stages` 存 JSONB，且可建索引 | 你的字段本来就是半结构化的，JSONB 比拆成一堆关联表灵活得多 |
| **pgvector** | 向量和业务数据同库，`ORDER BY embedding <-> $1 LIMIT 10` | V2 的 RAG 记忆层不用另起一个向量数据库，少一套运维 |

**代价必须说清楚，不美化：**

| 项 | 影响 |
|---|---|
| 服务器内存 | Postgres 至少要吃 1G，服务器从 2核2G 升到 **2核4G**（月成本约翻倍） |
| 运维复杂度 | 多一个容器、多一套备份方式（`pg_dump` 而不是 `cp`）、多一次冷启动等待 |
| 本地开发 | 要先起 Docker 里的 postgres，不能像 SQLite 那样"跑起来就有" |

**这笔账是划算的**：多花一点内存和一次 `docker compose up`，换到的是——多用户从第一天就是安全的、向量检索不用二次搭、字段演化不用反复改表。

> ⚠️ **RLS 必须从建表时就开始配**，不能等有了多用户再补。补的时候要回头审每一张表和每一条查询，成本是前者的十倍。

### 4.3.1 多用户隔离怎么做（四层，缺一不可）

| 层 | 做法 | 防什么 |
|---|---|---|
| **表结构** | 所有业务表强制带 `user_id`，且不可为空 | 从根上保证数据有归属 |
| **数据库层（RLS）** | `CREATE POLICY ... USING (user_id = current_setting('app.user_id')::int)` | 应用层写漏 where 也串不了数据 |
| **应用层** | 每个请求把当前用户写进 session 变量 `SET LOCAL app.user_id = ?` | RLS 需要这个变量才能生效 |
| **文件层** | `data/uploads/{user_id}/...` | 防止越权访问别人的原图 |

**登录形态（V1 最简）**：邀请制 + 邮箱密码。不做开放注册——种子用户是你自己和几个熟人，开放注册只会带来垃圾账号和隐私风险。

### 4.4 定时任务：为什么不用 Celery

APScheduler 跑在 FastAPI 进程内，每天 8 点扫事件、生成提醒。不需要 Redis、不需要 worker、不需要任务队列。

**代价**：进程重启会丢内存里的任务。所以任务必须**幂等**——每次扫"未来 7 天的事件"，而不是"给某条事件排一个定时器"。重启后重扫不会重复发。

### 4.5 模型：DeepSeek 主 + 通义备

**主通道 `deepseek-flash`**：
- 2026-09 起原生多模态（此前 `deepseek-v4-flash-vision-exp` 为实验版，现已路由到新名）
- OpenAI 兼容格式，`base_url=https://api.deepseek.com`
- 一张图最多 384 tokens，计费与文本同档
- 国内直连，无代理

**备通道 `qwen-vl-max`**：中文截图识别强，作为限流/故障/识别率下降时的降级。

**抽象层（必须做，半天工）**：

```python
# backend/app/services/vision.py
class VisionClient:
    def extract(self, image: bytes, prompt: str, schema: dict) -> dict:
        """统一入口，内部按 env 选 provider"""
```

```env
VISION_PROVIDER=deepseek          # deepseek | qwen
VISION_MODEL=deepseek-flash
FALLBACK_PROVIDER=qwen
FALLBACK_MODEL=qwen-vl-max
```

**为什么必须抽象**：答辩现场演示"换模型不改代码"靠它；论文里"模型可替换性"的实证也靠它。

> ⚠️ `deepseek-flash` 是实验模型转正，识图准确率**必须在前两周实测**。中文聊天截图字段抽取低于 75%，立刻切 `qwen-vl-max` 做主力，不要恋战。

### 4.7 DeepSeek Harness：V1 不接，V2 接

> 决定与接入方案见 [`ARCHITECTURE` 19.7](./ARCHITECTURE.md)。这里只留结论。

**V1 不接，不是因为不需要，是顺序**——助理要回答"谁喜欢喝茶"，得先有几百条事实；V1 前 8 周都在攒这些。

**V2 接，接法是侧车不是地基**：独立 Node 容器、只读、5 个查询工具。助理挂了，投喂提醒档案照跑。

**三个不能破的前提**：

| # | 前提 | 破了会怎样 |
|---|---|---|
| 1 | 业务真相只在 Postgres | 两套人物档案打架 |
| 2 | Harness 只能通过只读 API 访问 | 绕过 RLS，隔离失效 |
| 3 | 侧车不可用不影响主流程 | 地基变单点 |

**记忆的禁区**（最容易接错）：

| 类型 | 放哪 |
|---|---|
| 会话记忆（聊过什么） | ✅ Harness 自己存 |
| 工作记忆（任务中间态） | ✅ Harness 运行时 |
| **业务事实（王姐喜欢白茶）** | ❌ **只能在 Postgres，Harness 每次现查** |

一旦两个地方都存业务事实，用户改了一处、助理还记着旧的，就会出现"两个都对"。

**V1 结束时助理的插座天然存在**——数据都能通过现有只读 API 拿到，不需要为它提前建任何东西。

| Nginx | Caddy 自动 HTTPS，配置量 1/10 |
| Kubernetes | 一个人，一台机器 |
| Streamlit / Gradio | 移动端体验差，做不了卡片流 |
| 微信小程序 | 订阅消息一次性授权，长期提醒做不了 |
| JWT + localStorage | XSS 风险，且同域下没必要 |
| axios | fetch 够用，少一个依赖 |

### 7.2 docker-compose.yml 骨架

```yaml
services:
  db:
    image: pgvector/pgvector:pg17      # 自带 pgvector 扩展
    environment:
      POSTGRES_DB: keeper
      POSTGRES_USER: keeper
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pg_data:/var/lib/postgresql/data
    restart: unless-stopped
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U keeper -d keeper"]
      interval: 10s
      retries: 5

  app:
    build: ./backend
    depends_on:
      db:
        condition: service_healthy     # 等 db 真的能连上再起
    volumes:
      - ./data:/app/data               # 只放上传的截图，数据库不在这里
      - ./prompts:/app/prompts
    env_file: .env
    restart: unless-stopped

  web:
    build:
      context: ./frontend
      args:
        VITE_API_BASE: /api            # 同域，相对路径
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile
      - ./frontend/dist:/srv           # 或让 Caddy 直接托管 build 产物
      - caddy_data:/data               # 证书，必须持久化
    ports: ["80:80", "443:443"]
    restart: unless-stopped

volumes:
  caddy_data:
  pg_data:                             # 数据库卷，绝对不能丢
```

**`.env` 里新增一条**：

```env
DB_PASSWORD=换成一个长随机串
DATABASE_URL=postgresql+psycopg://keeper:${DB_PASSWORD}@db:5432/keeper
```

### 7.3 Caddyfile

```
yourdomain.com {
    handle /api/* {
        reverse_proxy app:8000
    }
    handle {
        root * /srv
        try_files {path} /index.html    # SPA 路由回退，必须写
        file_server
    }
}
```

> **`try_files {path} /index.html` 这行不能少**，否则刷新 `/person/3` 会 404。这是 SPA 部署最常见的坑。

## 九、技术风险与对冲

| 风险 | 概率 | 对冲 |
|---|---|---|
| **DeepSeek 识图准确率不够** | 中 | 前两周实测 30 张真实截图；低于 75% 切 `qwen-vl-max`；两路都不行则降级为"人工补录 + AI 辅助" |
| 备案拖过 20 天 | 中 | 备案期用 `http://IP:8000` 先开发；PWA 装不了但功能能测 |
| **前端吃时间超预期** | **中高** | 严格限制：不写复杂动画、不自己造组件库、不用冷门语法；每个页面先做"能看能用"的版本 |
| 前后端类型不同步 | 中 | 后端改 schema 就 `pnpm gen:types`，写进日常流程 |
| SPA 刷新 404 | 高（首次部署必遇） | Caddyfile 里 `try_files` 那行 |
| SQLModel 卡在复杂查询 | 中 | 复杂查询直接写 SQL |
| **RLS 配错，导致查不出任何数据** | **中高** | 应用连接必须用普通角色（不是 `postgres` 超级用户）；每建一张新表立刻加策略；**W1 就用两个账号互查验证**，不要等到有真实用户才发现 |
| 农历库跨年失效 | 中 | `FestivalService` 包一层，JSON 兜底 |
| 数据丢失 | 低但致命 | 每天 `pg_dump` 到另一块盘 + tar 打包 uploads，每月手动下载一份 |

## 十、这套栈的"AI 可维护性"

三个结构性优势：

1. **后端只有一个语言（Python）**，业务逻辑全在一处，AI 改抽取/提醒逻辑不会碰前端
2. **前端只有一个模式（`<script setup>` + Composition API）**，不用 React 的 hooks 心智模型，AI 生成的代码你能读懂
3. **接口契约由 OpenAPI 自动生成**，前后端字段不可能对不上——这消掉了 AI 改代码最容易引入的一类 bug

**反面例子**：如果前端用 React + 自研状态管理 + 手写类型，AI 改代码最容易出的错是"类型对不上但运行时才炸"。这套栈用自动生成的类型堵住了这个口子。

## 十一、一页纸结论

```
产品形态：响应式 Web + PWA（手机优先）
前端：    Vue 3 + TypeScript + Vite + Tailwind + Pinia + Vue Router
          + FullCalendar（日历）+ openapi-typescript（类型）
后端：    Python 3.13 + FastAPI + SQLModel + APScheduler
数据：    PostgreSQL 17 + pgvector + 本地文件
模型：    DeepSeek deepseek-flash（主）→ qwen-vl-max（备）
部署：    国内云 + Docker Compose + Caddy（同域托管前端 + 反代 API）
工具：    uv（后端）/ pnpm（前端）/ ruff / ESLint / pytest
```

**一句话**：**一个 Python API + 一个 Vue 静态包 + 一个 Postgres 实例。**
