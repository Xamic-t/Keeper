## 10. 本次验证发现的三个新缺陷

这三条是**跑出来的**，不是看代码想出来的。

### G5 · 500 响应没有 `X-Trace-Id` 头（严重）

| 项 | 内容 |
|---|---|
| 证据 | 验证脚本输出 `HAS_TRACE_ID_HEADER: False` |
| 原因 | 异常冒泡到中间件时被 `raise` 抛出，**中间件没机会设置响应头**；最终 500 由 Starlette 兜底返回，不经过我们的中间件 |
| 影响 | **恰恰是 500 这种最需要 trace_id 的场景，客户端拿不到它。** 用户报错时无法提供任何可定位的信息 |
| 正常请求 | ✅ 有头（`x-trace-id: 8908b5ddca23`） |
| 修复 | 在 `_handle_unexpected` 里读 `request.state.trace_id`，同时写进响应头和响应体 |

### G6 · 500 响应体里没有 `trace_id` 字段

| 项 | 内容 |
|---|---|
| 证据 | `BODY: {"error":{"code":"INTERNAL_ERROR","message":"服务器内部错误"}}` |
| 依据 | `10-接口响应规范` 5.5 节规定 500 必须带 `trace_id` |
| 影响 | 与 G5 叠加后，用户**完全没有任何可提供的信息** |
| 修复 | 同上，一次改动解决 G5 + G6 |

### G7 · 同一异常记两次日志（噪音）

| 项 | 内容 |
|---|---|
| 证据 | 日志里同时出现 `app.main` 的 "request failed" 和 `app.core.errors` 的 "unhandled error" |
| 原因 | 中间件 `except` 记一次 → `raise` → 全局 handler 又记一次 |
| 影响 | 一次故障产生两条 ERROR，排查时容易误判为两个问题；日志量大时更难看清 |
| 修复 | 二选一：中间件不记（让 handler 统一记），或 handler 不记（中间件已记） |

### 附：一处此前的判断需要更正

`11-封装边界审查` 里我写过：

> "中间件里用 `try/except` 包了 `call_next`……异常通常不会冒到这里……这段可能永远不触发。"

**实际验证证明我错了**：中间件的 `except` **确实会触发**（G7 的第一次记录就是它）。

这正好说明为什么要跑证据包——**光看代码会误判**。
