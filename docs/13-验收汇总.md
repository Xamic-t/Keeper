## 七、能不能开始写业务？

### 判断依据

只有 **P1** 会在建表时造成不可逆影响：

```
P1 不修 → 用 keeper（可能是 owner）建表 → RLS 策略写了也绕过 → 多用户隔离形同虚设
       → 而且不报任何错，测试也发现不了
```

其余 7 个都属于"错误处理的细节"，`services/`、`models/`、`api/` 的写法不受影响。

### 结论

| 问题 | 答案 |
|---|---|
| 能否开始写业务？ | **可以，但先修 P1** |
| P1 修复工作量 | 约 30 分钟（建角色 + 改配置 + 迁移加 `FORCE RLS`） |
| 其余 7 个什么时候修 | W2 结束前清零；P5 从第一个业务接口起就要遵守 |
| 未验收的 11 项 | 本来就要靠写业务来验证，不是开工条件 |
| 数据库连接未验证 | **必须在 W1 建表前补齐** |

### 开工前清单

```
□ 修 P1：创建 keeper_app 角色（非 owner）、改 DATABASE_URL
□ 补齐数据库连接验证（docker compose up -d db → check_database 返回 ok）
□ 建第一张表时，迁移里同时写 RLS 策略 + FORCE ROW LEVEL SECURITY
□ 写第一个业务接口时，必须用 response_model（P5）
□ W2 结束前修完 P2 / P3 / P4 / G7
```
