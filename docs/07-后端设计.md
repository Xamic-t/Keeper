## 1. 后端负责什么

### 1.1 职责边界

**后端负责**：

| # | 职责 | 说明 |
|---|---|---|
| 1 | **认证与授权** | 谁是谁、能看什么、不能看什么 |
| 2 | **数据持久化与隔离** | 15 张表的读写、RLS 多用户隔离 |
| 3 | **投喂处理** | 接收图片/文字、存盘、去重、异步调度抽取 |
| 4 | **AI 调用编排** | VLM 识图、结构化抽取、建议生成、失败降级 |
| 5 | **业务计算** | 画像综述重写、标签派生、关系价值累计、温度计算、提醒生成 |
| 6 | **定时任务** | 每日扫事件、生成提醒、发送推送 |
| 7 | **文件管理** | 上传、压缩、按人删除、打包导出 |
| 8 | **审计** | 抽取日志、路由日志，用于答辩和排错 |

**后端不负责**：

| 不做 | 谁做 |
|---|---|
| 页面渲染 | Vue（前端） |
| 交互状态（弹窗、选中、滚动位置） | 前端 |
| 图表绘制 | 前端 |
| 实时推送 | 企业微信 webhook（不是 WebSocket，不建长连接） |
| AI 对话上下文管理 | V2 才做，V1 无对话 |
| 权限矩阵配置界面 | V1 只有 owner/member 两种角色，写死 |

### 1.2 六条业务主线

后端的全部代码，最终都服务于这六条线：

```
① 投喂线   图片/文字 → 存储 → 异步抽取 → 确认队列 → 落库
② 画像线   事实变更 → 综述重写 → 标签派生 → 关系价值重算
③ 时间线   事件生成 → 日历查询 → 提醒扫描 → 推送 → 转待办
④ 查询线   人列表 / 档案 / 时间线 / 标签筛选
⑤ 治理线   认证 / 隔离 / 删除 / 导出 / 设置
⑥ 支撑线   定时任务 / 文件 / 审计
```

**判断一个函数该不该存在**：它属于上面哪条线？说不出来就是多余的。

## 2. 语言与框架（定稿）

### 2.1 一句话

> **Python 3.13 + FastAPI + SQLModel + PostgreSQL 17。**

### 2.2 为什么是它

| 理由 | 具体到这个项目 |
|---|---|
| Pydantic 校验抽取结果 | VLM 返回的 JSON 必须严格校验，字段缺失/类型错/多抽都是常态 |
| 自动 OpenAPI | 前端 TS 类型从 `/openapi.json` 生成，前后端字段永远一致 |
| 异步原生 | 调模型等几秒不阻塞其他请求 |
| 依赖注入适配 RLS | 每请求注入带 `SET LOCAL app.user_id` 的 session |
| **AI 熟悉度最高** | 出问题能搜到答案，比框架先不先进重要 |

### 2.3 框架自带 vs 需要额外库

**自带（不用装）**：

| 能力 | 用什么 |
|---|---|
| 路由分组 | `APIRouter` |
| 请求/响应校验 | Pydantic v2 |
| 依赖注入 | `Depends` |
| API 文档 | `/docs`、`/redoc`、`/openapi.json` 自动生成 |
| 异步 | `async def` |
| 后台任务 | `BackgroundTasks` |
| CORS | `CORSMiddleware` |
| 生命周期 | `lifespan`（连库、起 APScheduler） |
| 测试客户端 | `TestClient`（基于 httpx） |
| 文件上传解析 | `python-multipart`（唯一必装的小依赖） |

**需要额外库**：

| 能力 | 库 | 用在哪 |
|---|---|---|
| ORM | **SQLModel** | 15 张表的定义与查询 |
| 迁移 | **Alembic** | 建表、改表 |
| 配置 | **pydantic-settings** | 读 `.env` |
| 密码哈希 | **argon2-cffi** | 登录 |
| Cookie 签名 | **itsdangerous** | 会话、CSRF |
| 定时任务 | **APScheduler** | 每日 08:00 扫事件 |
| 图片处理 | **Pillow** | 压缩、裁边、转格式 |
| 出站 HTTP | **httpx** | 调 DeepSeek / 通义 |
| 模型 SDK | **openai**（官方 Python SDK） | DeepSeek 完全兼容 OpenAI 格式 |
| 农历 | **lunar-python** + **chinesecalendar** | 农历生日换算、法定节假日 |
| 向量 | **pgvector**（SQLAlchemy 扩展） | V2 的 RAG |
| 日志 | 标准 `logging` | 够用，不引 structlog |
| 代码质量 | **ruff** | lint + format |
| 测试 | **pytest** | service 层单测 |

**明确不用**：Redis、Celery、Django、Flask、Nginx、Kubernetes、GraphQL。

### 2.4 目录与分层

```
backend/
├── app/
│   ├── main.py           # 入口：lifespan、中间件、挂路由
│   ├── config.py         # pydantic-settings
│   ├── db.py             # 引擎、session、RLS 注入
│   ├── deps.py           # 依赖：当前用户、session、分页
│   ├── core/
│   │   ├── security.py   # argon2、cookie、CSRF
│   │   └── errors.py     # 统一异常
│   ├── models/           # SQLModel，对应 06 的 15 张表
│   ├── api/              # 路由：只解析参数、调 service、返回
│   ├── services/         # 业务逻辑：脱离 HTTP 可单测
│   └── jobs/             # APScheduler
├── prompts/
├── alembic/
└── tests/
```

**三条分层纪律**：

1. **`api/` 不写业务逻辑**——函数超过 30 行就说明放错了
2. **`services/` 不 import fastapi**（`HTTPException` 除外）——保证能脱离 HTTP 单测
3. **`models/` 只定义表，不写查询**——查询放 service，因为要带权限和业务条件

## 3. 认证与权限

### 3.1 认证方案

| 项 | 方案 |
|---|---|
| 登录凭证 | `username` + `password`（username 可填用户名/手机号/邮箱，不校验格式） |
| 密码存储 | **argon2id** 哈希 |
| 会话载体 | **httpOnly cookie**，签名内容为 `{user_id, exp}`，用 `itsdangerous` 签 |
| 有效期 | 7 天，滑动续期（每次请求刷新 exp） |
| CSRF | 登录时下发一个 token，写操作必须带 `X-CSRF-Token` 头 |
| 失败保护 | 连续 5 次锁 15 分钟（`users.failed_attempts` / `locked_until`） |
| 登出 | 清 cookie，无服务端状态需要清理 |

**为什么不用 JWT + localStorage**：XSS 能偷 token。同域部署下 cookie 更简单也更安全。详见 `05` 4.2.4。

### 3.2 权限模型

V1 只有两种角色：

| 角色 | 能做什么 |
|---|---|
| `owner` | 全部，含建号、禁用账号、重置密码 |
| `member` | 只能操作自己的数据 |

**注意**：角色管的是"功能权限"，不管"数据权限"。**数据权限完全由 RLS 保证**——member 之间也看不到彼此的数据。

### 3.3 权限校验放在哪一层

**三层，缺一不可**：

| 层 | 位置 | 管什么 | 失败返回 |
|---|---|---|---|
| **① 认证** | 路由依赖 `Depends(get_current_user)` | 有没有登录 | 401 |
| **② 数据隔离** | **数据库 RLS** | 能不能看别人的数据 | 自动过滤，查不到 → 404 |
| **③ 功能权限** | 路由依赖 `Depends(require_owner)` | 能不能用这个功能 | 403 |

**关键设计：越权访问返回 404 而不是 403。**

如果 A 访问 B 的 `person_id`，返回 403 等于告诉他"这个人存在"。返回 404 什么信息都不泄露。这是 RLS 自动过滤后的自然结果，不用额外写逻辑。

### 3.4 每个请求的执行顺序

```
请求进来
  ↓
① 中间件：解析 cookie → 拿 user_id（拿不到就 401，除白名单）
  ↓
② 依赖：开 db session → SET LOCAL app.user_id = <uid>   ← RLS 靠这一步生效
  ↓
③ 依赖：校验 CSRF（写操作）
  ↓
④ 路由函数：参数校验（Pydantic 自动）
  ↓
⑤ service：业务逻辑 + 业务校验
  ↓
⑥ 返回：统一包装
```

**第 ② 步不能省**。忘了 `SET LOCAL`，RLS 拿不到变量，查询会直接报错——**报错比静默泄漏好，但体验差**，所以这一步写在 `deps.py` 里统一做，不靠每个路由自己记得。

## 4. API 约定

### 4.1 基础

| 项 | 规则 |
|---|---|
| 路径前缀 | 全部 `/api` |
| 版本 | V1 不做路径版本号（只有你自己用，改了就改了） |
| 命名 | 资源用复数：`/api/persons`、`/api/events` |
| 方法 | GET 查、POST 建、PATCH 改、DELETE 删 |
| 内容类型 | `application/json`；上传用 `multipart/form-data` |
| 时间格式 | **ISO 8601 带时区**：`2026-10-27T08:00:00+08:00` |
| 日期格式 | `YYYY-MM-DD` |

### 4.2 统一响应格式

**成功**（2xx）：

```json
{
  "data": { ... },
  "meta": { "total": 18, "page": 1, "size": 20 }
}
```

单条资源 `meta` 可省。`204 No Content` 直接空响应。

**失败**（4xx / 5xx）：

```json
{
  "error": {
    "code": "PERSON_NOT_FOUND",
    "message": "找不到这个人",
    "detail": { "person_id": 19 }
  }
}
```

| 字段 | 规则 |
|---|---|
| `code` | **大写下划线**，稳定不变，前端用它判断分支，不看 message |
| `message` | 给人看的中文，可以改 |
| `detail` | 可选，结构化补充（哪个字段错了、冲突值是什么） |

### 4.3 错误码表

| HTTP | code | 什么时候 |
|---|---|---|
| 400 | `VALIDATION_ERROR` | 参数格式不对（Pydantic 自动抛） |
| 400 | `INVALID_STATE` | 状态不允许这个操作（如已确认的卡片再确认） |
| 401 | `UNAUTHENTICATED` | 没登录 / cookie 过期 |
| 401 | `BAD_CREDENTIALS` | 账号或密码错 |
| 401 | `ACCOUNT_LOCKED` | 连续失败被锁 |
| 403 | `FORBIDDEN` | 角色不够（member 访问 admin） |
| 404 | `NOT_FOUND` | 资源不存在**或不属于你** |
| 409 | `CONFLICT` | 唯一约束冲突（重复标签、重复提醒） |
| 413 | `FILE_TOO_LARGE` | 图片超限 |
| 422 | `UNPROCESSABLE` | 参数合法但业务上不能做（如删不存在的关联） |
| 429 | `RATE_LIMITED` | 请求过频（V1 只用在登录） |
| 500 | `INTERNAL_ERROR` | 未捕获异常，**不暴露堆栈** |
| 502 | `AI_UPSTREAM_ERROR` | 模型服务不可用（主备都失败） |
| 504 | `AI_TIMEOUT` | 模型超时 |

### 4.4 分页

V1 用最简单的 offset 分页：

```
GET /api/persons?page=1&size=20
```

| 参数 | 默认 | 上限 |
|---|---|---|
| `page` | 1 | — |
| `size` | 20 | 100 |

**为什么不用 cursor**：20 人规模，数据量到不了需要 cursor 的程度。**不要为了技术正确而复杂化。**

### 4.5 参数校验规则

| 类型 | 规则 |
|---|---|
| 文本 | 去首尾空格；`nickname` 1-50 字；`content` 1-2000 字 |
| 金额 | `> 0`，最多两位小数 |
| 日期 | `YYYY-MM-DD`，不能是 9999 年以后 |
| 枚举 | 必须命中白名单，**不在白名单直接 400**，不静默降级 |
| 图片 | jpg/png/webp；单张 ≤ 8MB；一次最多 10 张 |
| ID | 正整数 |

### 4.6 幂等性

三个地方必须幂等，否则会出重复数据：

| 场景 | 怎么保证 |
|---|---|
| 上传同一张图 | `raw_inputs` 有 `UNIQUE(user_id, file_hash)`，重复直接返回已存在的那条 |
| 同一事件同一档提醒 | `reminders` 有 `UNIQUE(event_id, remind_on, level)` |
| 定时任务重跑 | 任务本身写成"扫未来 7 天"，不是"排一个定时器" |

### 5.2 核心 API 详细规格

只详细写 8 个——它们覆盖了全部核心流程，其余按同样的模式推导。

---

#### ① `POST /api/ingest/image` — 上传截图

**用途**：投喂主入口。手机相册多选上传。

**权限**：登录。**CSRF 必须校验。**

**请求**：
```
Content-Type: multipart/form-data
files: File[]        1-10 张
person_id?: int      可选，手动指定归属
```

**响应** `202 Accepted`：
```json
{
  "data": {
    "items": [
      { "raw_input_id": 101, "status": "pending", "duplicate": false },
      { "raw_input_id": 102, "status": "pending", "duplicate": true,
        "existing_id": 88 }
    ]
  }
}
```

**读写的表**：`raw_inputs`（写）、`persons`（读，校验归属人属于当前用户）

**业务校验**：

| # | 校验 | 失败 |
|---|---|---|
| 1 | 张数 1-10 | 400 `VALIDATION_ERROR` |
| 2 | 单张 ≤ 8MB，格式 jpg/png/webp | 413 / 400 |
| 3 | 算 sha256，同一用户已有同 hash → **返回已有记录，不重复存** | 200 + `duplicate: true` |
| 4 | 传了 `person_id` 时必须属于当前用户 | 404 `NOT_FOUND` |
| 5 | 用户关闭了原图留存 → 处理完后删图 | — |

**异常**：

| 情况 | 返回 |
|---|---|
| 全部重复 | 200（不是错误） |
| 磁盘写失败 | 500 `INTERNAL_ERROR` |
| 队列塞满 | 429 `RATE_LIMITED` |

**异步部分**：立即返回 202，抽取在 `BackgroundTasks` 里跑。前端轮询 `GET /api/raw-inputs/{id}` 或等 `GET /api/confirmations` 出现新卡片。

#### ③ `POST /api/confirmations/{id}/confirm` — 确认一条

**用途**：把抽取结果落进档案。

**权限**：登录 + CSRF。

**请求**：`{ "kind": "fact" }`

**响应**：
```json
{
  "data": {
    "fact_id": 301,
    "status": "confirmed",
    "cascaded": {
      "summary_rewritten": true,
      "tags_derived": 2,
      "relevance_recalculated": true
    }
  }
}
```

**读写的表**：`facts`（写 status）、`tags`（派生写入）、`relationships`（重算价值）、`persons`（触发综述重写）

**业务校验**：

| # | 校验 | 失败 |
|---|---|---|
| 1 | 该 fact 属于当前用户 | 404 |
| 2 | 当前状态必须是 `pending` | 400 `INVALID_STATE` |
| 3 | 若 category 是 `taboo`，内容不能为空 | 400 |

**副作用（级联）**：这一步是本项目最复杂的写操作，必须在一个事务里：

```
① facts.status = 'confirmed'，last_confirmed_at = now()
② 派生 tags（按 category 映射 key）
③ 重算 relationships.total_in / total_out（若涉及 ledger）
④ 标记 persons 的综述需要重写（不在这里同步调模型，写入一个待办标记）
```

> **综述重写不放在请求里**，因为要调模型（几秒）。改为写入标记，由后台任务或下次读档案时懒生成。**用户点确认必须立刻响应，不能等模型。**

**异常**：

| 情况 | 返回 |
|---|---|
| 已确认过 | 400 `INVALID_STATE` |
| 已被删除 | 404 |
| 派生标签冲突 | 忽略（`ON CONFLICT DO NOTHING`） |

#### ⑦ `DELETE /api/persons/{id}` — 删除一个人

**用途**：隐私承诺的兑现。

**权限**：登录 + CSRF。

**响应**：`204 No Content`

**读写的表**：`persons`（删）、级联 10 张表

**业务校验**：

| # | 校验 | 失败 |
|---|---|---|
| 1 | 人属于当前用户 | 404 |
| 2 | （可选）二次确认由前端做，后端不拦 | — |

**执行顺序（重要）**：

```
① 查出该人所有 raw_inputs 的 file_path
② 数据库事务：DELETE FROM persons WHERE id=?  → 级联删 10 张表
③ 事务提交后，删文件（文件操作不能放在事务里）
④ 若文件删除失败，记日志，不回滚（数据已删，文件残留可后续清理）
```

**为什么文件删除放事务外**：文件系统不支持事务回滚。先删数据库再删文件，最坏情况是残留孤儿文件（可清理）；反过来最坏情况是数据还在但文件没了（用户看到破图，体验更差）。

**异常**：删不存在的 → 404。

#### ⑧ `POST /api/auth/login` — 登录

**用途**：唯一不需要登录的写接口。

**权限**：公开。**不限流会被爆破，必须限。**

**请求**：`{ "username": "xamic", "password": "..." }`

**响应**：
```
200
Set-Cookie: session=<签名>; HttpOnly; Secure; SameSite=Lax; Max-Age=604800
Set-Cookie: csrf=<随机串>; Secure; SameSite=Lax   ← 前端可读，用于回传 header
```

```json
{ "data": { "user": { "id": 1, "username": "xamic", "display_name": "Xamic", "role": "owner" } } }
```

**读写的表**：`users`（读 + 写 `failed_attempts` / `locked_until` / `last_login_at`）

**业务校验**：

| # | 校验 | 失败 |
|---|---|---|
| 1 | `locked_until > now()` | 401 `ACCOUNT_LOCKED`（告诉还要等多久） |
| 2 | 账号存在且 `is_active` | 401 `BAD_CREDENTIALS`（**不区分"账号不存在"和"密码错"**） |
| 3 | argon2 校验通过 | 同上 + `failed_attempts += 1` |
| 4 | 失败累计 ≥ 5 → `locked_until = now() + 15min` | — |
| 5 | 成功 → 失败计数清零，写 `last_login_at` | — |

**安全细节**：

- 账号不存在和密码错**返回同一个错误**，防止枚举账号
- 锁定中的账号也要先校验密码再报锁定？——**不，先报锁定**，避免被用来试密码
- 登录接口按 IP 限流 10 次/分钟

## 6. 业务校验规则汇总

### 6.1 通用（所有写接口）

| # | 规则 | 实现位置 |
|---|---|---|
| 1 | 必须登录 | 路由依赖 |
| 2 | 写操作必须校验 CSRF | 中间件 |
| 3 | 数据必须属于当前用户 | **RLS**（不靠手动 where） |
| 4 | 参数必须通过 Pydantic 校验 | 路由签名 |
| 5 | 枚举值必须在白名单 | Pydantic `Literal` |
| 6 | 违反唯一约束要转成 409，不是 500 | 全局异常处理 |

### 6.2 分模块特有

| 模块 | 规则 |
|---|---|
| **人** | 删除前不需检查关联（全删）；`nickname` 不唯一，允许重名 |
| **关系** | `stage` 改成 `manual` 后，自动算法不再覆盖；`birthday_type` 和 `birthday_solar/lunar` 必须配套 |
| **事实** | 只有 `pending` 能确认/驳回；`confirmed` 的可以删但不能改 category |
| **往来** | `amount > 0`；`due_date >= occurred_at`；删往来要重算 `relationships.total_*` |
| **事件** | `type=birthday` 必须挂人；`type=festival` 不能挂人；农历事件必须有 `lunar` 字段 |
| **提醒** | 同事件同档不能重复；`status=sent` 才能转待办；不能转两次 |
| **待办** | 已完成（`done`）的不能再改回 `open`（要改先复制一条） |
| **账号** | 不能删自己；不能禁用最后一个 owner |

## 7. 数据访问规则

### 7.1 哪些表只读（业务接口不许直接写）

| 表 | 谁写 |
|---|---|
| `tags` | **只有确认事实和重算时写**，接口不直接写 |
| `relationships.total_in/out` | **只能通过重算函数写**，接口不直接改 |
| `extraction_logs` | 只有抽取链路写 |
| `temperature_snapshots` | 只有定时任务写 |

### 7.2 事务边界

| 操作 | 事务范围 |
|---|---|
| 确认一条事实 | 事实 + 标签 + 关系重算 + 综述标记，**同一事务** |
| 删除一个人 | 数据库删除在一个事务；**文件删除在事务外** |
| 新增往来 | 往来 + 重算 `total_*`，**同一事务** |
| 上传图片 | 只写一条 `raw_inputs`，单条自动提交 |

**原则**：一个业务动作要么全成要么全败；跨系统的操作（文件、外部 API）必须放在事务外。

### 7.3 不依赖"应用层记得过滤"

所有 `SELECT` 都不写 `WHERE user_id = ?`——**RLS 会加**。

**唯一例外**：`users` 表没开 RLS（登录前查不到 user_id），登录查询要手动按 `username` 过滤。

### 7.4 缓存

**V1 不做缓存。** 18 个人的数据，每次查库都是毫秒级。

唯一考虑的"缓存"是画像综述：生成慢，所以用 `summary_stale` 标记，懒生成——**这是懒计算，不是缓存**。

## 8. 异常与降级

### 8.1 后端能挂在哪

| 位置 | 后果 | 处理 |
|---|---|---|
| **数据库挂** | 全站不可用 | `/api/health` 探测；Docker `restart: unless-stopped` |
| **模型挂** | 投喂能传不能抽；提醒能发但没建议 | 主备切换；都失败则降级为"待人工补录" |
| **推送通道挂** | 提醒发不出 | 企微失败 → PushPlus；都失败记 `failed`，下次重试 |
| **磁盘满** | 上传失败 | 返回 507；提供"仅留文字"开关 |

### 8.2 降级策略（按优先级）

```
模型主通道失败 → 重试 1 次 → 切备通道 → 都失败：
  ├─ 投喂：raw_inputs.status = 'failed'，前端提示"这张没读懂，可以手动记一条"
  └─ 提醒：只发日期 + 事实陈述，不生成建议（标记 degraded=true）
```

**永远不要让模型故障导致"数据丢失"**。图片先存下来，抽取失败可以重试。

### 8.3 日志

| 级别 | 记什么 |
|---|---|
| `INFO` | 请求路径、耗时、状态码 |
| `WARNING` | 模型降级、推送失败、抽取置信度全低 |
| `ERROR` | 未捕获异常（带 trace_id，**不记密码和完整 cookie**） |

**不记**：请求体里的密码、完整图片内容、用户的私人聊天文本（只在 `raw_inputs.ocr_text` 里存）。
