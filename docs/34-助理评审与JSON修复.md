# 34 · 助理代码评审与 JSON 报错修复（2026-11-03 03:10）

> 触发：用户反馈「发了好多次都提示 JSON 格式错误」。
> 做法：先按 `ARCHITECTURE` 逐条评审助理相关代码 → 定位根因 → 修 → 用真实模型复测。
> 结论：**不是"模型偶尔抽风"，是我们在多轮对话里用错了 `response_format`。**

---

## 一、根因（探针实测，不是猜）

我写了一个探针，把同一段上下文按 4 种请求形态各打 5 次，统计"返回空白"的比例：

| 形态 | messages | 空白率 |
|---|---|---|
| ① `response_format=json_object` + 关思考 | 带 9 条历史 | **5/5 空白** |
| ② `response_format=json_object` + 开思考 | 带 9 条历史 | **5/5 空白** |
| ③ 不带 `response_format` + 关思考 | 带 9 条历史 | 0/5 |
| ④ 不带 `response_format` + 开思考 | 带 9 条历史 | 0/5 |

关键点：空白响应的 `finish_reason` 是 **`stop`**，`content` 为空、`reasoning_content` 有内容。
也就是说模型"想完了但没给正文"，而我们的代码把它当成"模型没有返回合法 JSON"报给用户——
**同一个现象，错误提示指错了方向**（用户以为是自己发的格式不对）。

进一步对比（每种 5 次）：

| 方案 | JSON 命中 |
|---|---|
| 现状（system 里要求 JSON，无 `response_format`） | 0/5（全回散文） |
| **末尾补一句"只输出 JSON"** | **5/5** |
| `response_format` + 截短历史 | 1/5 |
| `response_format` + 末尾指令 | 5/5 |

**采用的组合**：不开 `response_format` + 末尾硬约束 + 关思考 + 容错解析 + 重试 + 兜底。
理由：不依赖那个会抽风的参数，最坏情况只是"这次不建待办，但有话回"。

## 三、修完之后的可靠性（同一套探针复测）

| 场景 | 修前 | 修后 |
|---|---|---|
| 带 9 条历史连打 15 次 | `ok 6 / 降级 9 / 失败 0`（60% 只能给纯文本） | **`ok 15 / 降级 0 / 失败 0`** |
| 换 5 种说法连打 20 次（无历史） | 有 1~2 次空白报错 | **20/20** |
| HTTP 端到端连打 6 次（真实账号、真实历史） | 3/5 报「模型返回了空内容」 | **6/6 200** |

失败时用户看到的变化：

| 场景 | 修前 | 修后 |
|---|---|---|
| 模型两次都不给 JSON | 红字「模型没有返回合法 JSON」 | 第三次要纯文本 → 正常一句话（本次不建待办） |
| 连纯文本都拿不到 | 同上 | 「刚才没接上（原因）。点重试我再答一次——你的话已经存下了，不会丢。」 |
| 点重试 | 会话里出现两条一样的用户消息 | 复用原消息，只补一条回复 |

## 五、遗留（不影响今晚使用）

| 项 | 说明 |
|---|---|
| 模型侧行为依赖 | 我们不再用 `response_format` 做保证，靠"末尾约束 + 容错解析 + 重试 + 兜底"四层。若某天模型连散文都不回，用户仍会看到 502+重试，属预期兜底 |
| 抽取链路未动 | 抽取是**单轮**请求，`response_format` 在那条链路上没有空白问题（实测），保持原样，避免影响既有准确率 |
| 多会话 / 语音 | V2（见 `docs/29`） |
| 历史裁剪 | 现在带最近 8 轮；对话变长后若再次出现异常，优先怀疑上下文过长，可降到 4 轮 |
