# 09 · 最小模块演练：「人」模块

> **目的**：验证 ARCHITECTURE v2.1 的分层设计在真实业务里能不能落地。
> **范围**：只输出文件清单与调用路径，**不写完整业务代码**。
> **选它的原因**：最小、但覆盖全链路——读写两条路径、参数校验、权限、事务、统一响应、统一错误，一个都不缺。

---

## 1. 演练的接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/persons` | 人列表（分页、搜索） |
| `POST` | `/api/persons` | 手动新建一个人 |

选这两个，因为 `06-数据库设计` 里有一个关键约束：**`persons` 和 `relationships` 是 1:1**，建人时必须同时建关系。这能验证事务边界。

## 3. 每个文件的职责（详细）

### 3.1 `app/models/person.py`

```python
class Person(SQLModel, table=True):
    __tablename__ = "persons"

    id: int | None = Field(default=None, primary_key=True)
    user_id: int = Field(foreign_key="users.id", ondelete="CASCADE")
    nickname: str = Field(max_length=50)
    aliases: list[str] = Field(default_factory=list, sa_column=Column(JSONB))
    platform_ids: dict[str, str] = Field(default_factory=dict, sa_column=Column(JSONB))
    avatar_path: str | None = None
    contact: dict[str, str] = Field(default_factory=dict, sa_column=Column(JSONB))
    note: str | None = None
    created_at: datetime = Field(default_factory=...)
    updated_at: datetime = Field(default_factory=...)
```

**职责边界**：只有字段、约束、索引声明。**没有一行查询。**

### 3.2 `app/models/relationship.py`

```python
class Relationship(SQLModel, table=True):
    __tablename__ = "relationships"

    person_id: int = Field(foreign_key="persons.id", ondelete="CASCADE", unique=True)
    roles: list[str] = Field(default_factory=lambda: ["ge_jie"], sa_column=Column(JSONB))
    stage: str = Field(default="new")          # new/familiar/core/cold
    stage_source: str = Field(default="auto")  # auto/manual
    birthday_solar: date | None = None
    birthday_lunar: dict | None = Field(default=None, sa_column=Column(JSONB))
    taboo: list[str] = Field(default_factory=list, sa_column=Column(JSONB))
    total_in: Decimal = Field(default=Decimal("0"), max_digits=12, decimal_places=2)
    total_out: Decimal = Field(default=Decimal("0"), max_digits=12, decimal_places=2)
    is_active: bool = Field(default=True)
    ...
```

**关键**：`person_id` 上的 `unique=True` 就是 1:1 约束，这是数据库层保证的，不靠业务代码。

### 3.3 `app/services/person.py`

```python
async def list_persons(
    session: AsyncSession,
    pagination: Pagination,
    keyword: str | None = None,
) -> tuple[list[Person], int]:
    """列表 + 总数。不需要 user_id——RLS 会自动过滤。"""

async def create_person(
    session: AsyncSession,
    user_id: int,          # 写操作必须显式传，因为要写进 user_id 字段
    payload: PersonCreate,
) -> Person:
    """建人。persons 和 relationships 必须在同一事务里。"""
```

**这里有两条业务规则，都写在这一层**：

| 规则 | 为什么在 service |
|---|---|
| 建人时**同时建 relationship**（1:1 不能只有一半） | 这是业务约束，不是参数校验 |
| **昵称允许重复**（不查重） | 业务判断：可能有两个"王姐"，靠头像和标签区分 |

**这一层不 import fastapi**——所以 `pytest tests/services/test_person.py` 可以不起 HTTP。

### 3.4 `app/api/persons.py`

```python
router = APIRouter(prefix="/api/persons", tags=["persons"])

class PersonCreate(BaseModel):
    nickname: str = Field(min_length=1, max_length=50)
    roles: list[Literal["ge_jie", "customer"]] = ["ge_jie"]
    ...

class PersonListItem(BaseModel): ...
class PersonDetail(BaseModel): ...

@router.get("", response_model=...)          # ← 注意 response_model
async def list_persons(
    pagination: Annotated[Pagination, Depends(get_pagination)],
    keyword: str | None = Query(None, max_length=50),
    session: Annotated[AsyncSession, Depends(get_session)],
) -> ...:
    items, total = await person_service.list_persons(session, pagination, keyword)
    return ok([...], meta={...})             # ← 统一响应

@router.post("", status_code=201, response_model=...)
async def create_person(
    payload: PersonCreate,
    user: Annotated[CurrentUser, Depends(get_current_user)],
    session: Annotated[AsyncSession, Depends(get_session)],
) -> ...:
    person = await person_service.create_person(session, user.id, payload)
    return ok(...)
```

**这个文件只做三件事**：接参数、调 service、包响应。**没有一行 if 判断业务**。

## 4. 调用路径

### 4.1 `GET /api/persons?page=1&size=20&keyword=王`

```
① HTTP 请求
      ↓
② main.py · access_log 中间件
      · 生成 trace_id = "a1b2c3"
      · 记开始时间
      ↓
③ main.py · include_router 把 /api 交给 api_router
      ↓
④ api/router.py · 匹配到 persons.router（prefix="/api/persons"）
      ↓
⑤ api/persons.py · list_persons() 的依赖链开始解析（FastAPI 自动）
      │
      ├─ Depends(get_pagination)
      │     └─ Pydantic 校验 page≥1、size∈[1,100]
      │        失败 → RequestValidationError → core/errors.py → 400 VALIDATION_ERROR
      │
      └─ Depends(get_session)
            ├─ 内部 Depends(get_current_user)
            │     └─ 未登录 → AppError(UNAUTHENTICATED) → 401
            └─ SET LOCAL app.user_id = 1     ← RLS 从这一刻生效
      ↓
⑥ api/persons.py · 调 person_service.list_persons(session, pagination, keyword)
      ↓
⑦ app/services/person.py
      · select(Person).where(nickname ilike ...)     ← 不写 where user_id
      · 同条件 count(*)
      · RLS 自动追加 user_id = 1
      ↓
⑧ app/models/person.py · Person 表定义被 SQLModel 转成 SQL
      ↓
⑨ 返回 list[Person] + total
      ↓
⑩ api/persons.py · 转成 list[PersonListItem]
      ↓
⑪ core/response.py · ok(items, meta={total, page, size})
      ↓
⑫ main.py · access_log 记完成（status=200, duration_ms=12）
      ↓
⑬ { "data": [...], "meta": {...} }
```

### 4.2 `POST /api/persons`（body: `{"nickname": "王姐"}`）

```
① HTTP 请求
      ↓
②③④ 同上
      ↓
⑤ api/persons.py · create_person()
      ├─ Pydantic 校验 body
      │    · nickname 缺失 / 空 / 超 50 字 → 400 VALIDATION_ERROR
      │    · roles 不在 ["ge_jie","customer"] → 400 VALIDATION_ERROR
      └─ Depends(get_session) → 认证 + SET LOCAL
      ↓
⑥ api/persons.py · 调 service，传 user.id
      ↓
⑦ app/services/person.py · create_person()
      · 业务规则 1：昵称允许重复 → 不查重
      · 业务规则 2：必须同时建 relationship
      │
      └─ async with session.begin():        ← 事务边界
             insert persons(user_id=1, nickname="王姐")
             insert relationships(person_id=<new>, roles=["ge_jie"], stage="new")
      ↓
⑧ models 把两个 insert 转成 SQL
      ↓
⑨ 返回 Person
      ↓
⑩ 组装 PersonDetail，status_code=201
      ↓
⑪⑫⑬ 同上
```

**如果第 ⑧ 步的第二个 insert 失败**（比如外键错），事务回滚，`persons` 里也不会留下半条记录。

## 5. 八个问题

| 问题 | 答案 | 具体位置 |
|---|---|---|
| **请求从哪里进入？** | `main.py` 的中间件 → `router.py` 分发 | ①→②→③→④ |
| **参数在哪里校验？** | 路由函数签名上的 Pydantic 模型，**框架自动执行** | ⑤（`PersonCreate`、`Query`、`Pagination`） |
| **业务规则在哪里处理？** | `services/person.py` | ⑦（同时建关系、允许重名） |
| **数据访问在哪里处理？** | **查询在 service**，表定义在 model，session 从 deps 注入 | ⑦ + ⑧ |
| **统一响应在哪里处理？** | `core/response.py` 的 `ok()`，在路由最后一步调用 | ⑪ |
| **统一错误在哪里处理？** | `core/errors.py` 的 4 个全局 handler，**路由里一行 try/except 都没有** | ⑤ 的参数错、⑧ 的数据库错 |
| **权限在哪里校验？** | `deps.py` 的三层，通过 `Depends` 挂在路由上 | ⑤ |
| **新增模块要改哪些既有文件？** | 只有 2 个：`api/router.py` 加一行、`models/__init__.py` 导出 | 2.2 节 |

## 7. 这次演练暴露的三个问题（架构层面的）

演练的价值不是"证明能跑"，是**提前发现设计漏洞**。

### 问题 A · `relationships` 的 `user_id` 冗余怎么保证一致

`06` 里 `relationships` 同时有 `user_id` 和 `person_id`。建关系时两个都要写，如果写漏 `user_id`，RLS 就保护不了这张表。

**建议**：在 `create_person` 里只从一个来源取 `user_id`（`current_user.id`），不要分别传两次。

### 问题 B · 列表的 `count(*)` 会被 RLS 影响吗

会——RLS 自动过滤，所以 `count(*)` 得到的就是"你自己的数量"，正是想要的。

**但要注意**：如果以后加"全站统计"（管理员看总量），必须用 `get_raw_session`，否则永远只能看到自己的。

### 问题 C · 删除人的时候，`todos.person_id` 是 `SET NULL`

演练只覆盖了增和查。真正实现删除时会发现：删掉王姐，她那句"给王姐发问候"的待办**还在**，只是没归人了。

**这是 `06` 里定的规则（唯一不级联的业务表）**，实现时要显式处理，不能想当然以为全删了。
